## 二、⭐ 评测代码的可信度（在报数字之前必须先证明）

> **指标算错，则下面所有数字都无意义。** 这是 [docs/09](09-实施计划.md) M2.3 定为硬门槛的原因。

### 2.1 实现与验证

| 验证手段 | 结果 |
|---|---|
| 单元测试（含 [docs/05](05-评测协议.md) 全部人工算例） | ✅ **52/52 通过** |
| 引擎：`src/eval/metrics.py` | Recall / Precision / MRR / nDCG，含 `DCG ≤ IDCG` 硬断言 |

### 2.2 ⭐ 真实数据交叉验证（比单测更有说服力）

用真实 dev 语料构造三种极端排序，看指标是否给出预期行为：

| 排序方式 | Recall@10 | nDCG@10 | Recall@100 | nDCG@100 | 含义 |
|---|---|---|---|---|---|
| **oracle**（相关全排最前） | 0.9946 | **1.0000** | **1.0000** | **1.0000** | 完美排序 |
| **random**（随机取 100 段） | 0.0000 | 0.0000 | 0.0000 | 0.000089 | 随机基线 |
| **anti**（相关全压到最后） | 0.0000 | 0.0000 | **1.0000** | **0.1869** | ⭐ **召回满、排序差** |

**⭐ 最关键的一行是 anti**：

```
anti 的 Recall@100 = 1.0（相关段落全在库里，全都召回了）
但 nDCG@100 只有 0.1869（因为排在了最后）
        ↓
这证明：指标能区分「召回」与「排序质量」两件事
        ↓
而这两件事的分离，正是 E3「重排序」实验成立的前提
```

> 若指标无法区分这两者，E3 就无从设计、也无法解释其收益来源。

**random 的 nDCG@100 ≈ 0.000089 也符合理论量级**：100 段随机取自 10 万段，
命中的期望概率约 $100 \times 2.6 / 100000 \approx 0.26\%$，与实测同数量级。

完整报告：[`data/processed/metrics_verify_dev.json`](../data/processed/metrics_verify_dev.json)

| 指标 | 默认 (1.5) | 调优 (0.7) | 差值 | 相对 | p 值 | Cohen's d |
|---|---|---|---|---|---|---|
| **nDCG@10** | 0.5199 | **0.5305** | +0.0107 | **+2.05%** | 7.5e-26 | **0.114** |
| Recall@10 | 0.6033 | 0.6102 | +0.0069 | +1.15% | 8.2e-06 | 0.048 |
| nDCG@100 | 0.5626 | 0.5721 | +0.0094 | +1.68% | 1.5e-27 | 0.117 |
| Recall@100 | 0.7712 | 0.7741 | +0.0029 | +0.38% | 1.5e-02 | 0.026 |

nDCG@10 的 95% bootstrap 置信区间：**[+0.0087, +0.0127]**（不含 0）
逐 query 分布：变好 1,533 / 变差 1,030 / **不变 6,077（70.3%）**

**⚠️ 必须如实报告的矛盾结论：**

```
统计显著（p = 7.5e-26）  ≠  实际重要（效应量 d = 0.114 属"可忽略"）

原因：样本 8,640 条足够大，2% 的微小差异也能测出显著性；
      但 70% 的 query 结果完全没变，提升集中在少数 query 上。

⭐ 因此本项目对 B1 的表述是：
   "调参带来统计显著但幅度有限的提升（nDCG@10 +2.05%，效应量小）"
   而【不是】"调参大幅提升检索效果"。
```

## 四、⭐ 稠密检索结果（D1 / D2）

### 4.1 实现要点

| 项 | 设置 | 理由 |
|---|---|---|
| 模型 | D1: `bge-small-zh-v1.5`（512 维）<br>D2: `bge-base-zh-v1.5`（768 维） | 同系列不同规模，可控对比 |
| 归一化 | ✅ L2 归一化 | 归一化后内积 = 余弦相似度 |
| 索引 | `faiss.IndexFlatIP` | 精确检索（非近似），10 万段无需 IVF |
| query 指令 | `为这个句子生成表示以用于检索相关文章：` | BGE 官方推荐用法 |
| max_length | 512 tokens | ⚠️ 超长段落会被截断（见局限） |
| 精度 | fp16（GPU） | 提速约 2.5× |

### 4.4 ⭐ 互补性分析（这是 E2 的直接动机）

| 对比 | Top-10 平均 IoU | 并集能多命中的 query 数 |
|---|---|---|
| **BM25(调优) vs D1** | **0.2143** | **3,169 / 8,640（36.7%）** |
| D1 vs D2 | 0.3956 | 1,468 / 8,640（17.0%） |

```
⭐ 关键发现：BM25 与稠密检索的 Top-10 只有 21.4% 重合

  → 两者看过的大部分文档是【不同】的
  → 在 36.7% 的 query 上，两个结果取并集能找回更多相关文档
      ↓
  ⭐ 这正是 E2「混合检索（RRF）」的量化动机：
     不是"理论上应该互补"，而是"实测确实只重合 21%"。
```

### 4.6 ⭐⭐ 一个必须报告的负面结果：BGE query 指令反而降低效果

**背景**：BGE 官方文档建议检索时给 query 加指令前缀
`"为这个句子生成表示以用于检索相关文章："`。我在初版实现中**按官方推荐默认启用了它**。

**排查过程**（2026-10-24 复核时发现）：

```
在核对"我的设计选择是否合理"时，做了消融实验，结果与官方推荐相反：
      ↓
   BGE-small:  带指令 0.7238  →  不带指令 0.7332  （+1.30%）
   BGE-base :  带指令 0.7936  →  不带指令 0.8139  （+2.56%）
      ↓
   两者 p 值分别 8.0e-13 / 3.8e-51，95% CI 均不含 0 → 显著
```

| 模型 | 带指令 nDCG@10 | 无指令 nDCG@10 | 差异 | p 值 | Cohen's d |
|---|---|---|---|---|---|
| BGE-small | 0.723848 | **0.733224** | **+1.30%** | 8.0e-13 | 0.077 |
| BGE-base | 0.793555 | **0.813905** | **+2.56%** | 3.8e-51 | 0.163 |

**逐 query 分布**：small 上无指令更好 1,854 条 / 带指令更好 1,405 条（其余相同）。

**已做的修正**：

1. `src/retrieval/dense.py` 的默认值改为 `DEFAULT_QUERY_INSTRUCTION = ""`
2. D1/D2 结果**全部重跑**（旧的带指令结果已删除）
3. 新增 `scripts/ablate_query_instruction.py` 可复现该结论

**⭐ 为什么这个发现值得写进报告**：

```
① 它是一次【自查发现的错误】，不是"跑出好看数字就算了"
② 它与官方推荐相反 —— 说明"官方默认"不等于"你的数据上最优"
③ BGE v1.5 模型卡其实写了「v1.5 即使不加指令也不会有明显性能下降」，
   我的初版实现只看了"检索任务要加指令"的旧文档，没读 v1.5 的更新说明
④ 差距 1.3%~2.6% 虽小但显著，若不复核会一直带着这个偏差
```

> ⚠️ **附带发现的一个工程缺陷**：索引缓存的文件名原本不含配置项，
> 导致我改了默认值后**仍命中旧缓存、结果不变**。已修正为缓存键包含
> `query_instruction` 标记，并在载入时校验配置一致性。

## 六、⭐ 结论（E1 完成版，dev 集）

### ✅ Q1 的答案：稠密检索显著优于 BM25

| 方法 | nDCG@10 | Recall@10 | 相对 BM25(调优) |
|---|---|---|---|
| BM25（调优 k1=0.7） | 0.5305 | 0.6102 | — |
| D1 / BGE-small | **0.7332** | **0.8151** | **+38.2%** |
| D2 / BGE-base | **0.8139** | **0.8875** | **+53.4%** |

**三个层次的结论：**

**① 稠密检索比 BM25 强很多，且差距是"实质性"的**

```
nDCG@10:  0.5305 → 0.7332（+38.2%）
效应量:    Cohen's d = 0.613（中等效应）
p 值:      < 1e-300（8,640 条配对样本）
```

**② ⭐ "换方法"远比"调参数"重要 —— 本实验最有价值的观察**

| 改进方式 | nDCG@10 提升 | 效应量 | 判定 |
|---|---|---|---|
| BM25 调参（k1 1.5→0.7） | +2.05% | **0.114** | 可忽略 |
| **换成稠密检索** | **+38.2%** | **0.613** | **中等** |
| 稠密小模型 → 大模型 | +11.0% | 0.391 | 小 |

> 这张表对工程实践的含义：**先选对范式，再优化参数**。
> 花 5 小时调 BM25 的超参，不如花 70 秒编码一次向量。

**③ 模型规模的边际收益递减**

```
BGE-small → BGE-base：
  nDCG@10 +11.0%（0.7332 → 0.8139）
  但编码时间 4.0 倍（62s → 251s）
  向量维度 1.5 倍（512 → 768）
      ↓
  是否值得，取决于场景对延迟/成本的容忍度
```

### ⭐ 为 E2 提供的直接动机

```
BM25 与 D1 的 Top-10 平均 IoU 仅 0.2143
  → 两者检索到的文档 【只有 21.4% 重合】
  → 在 3,169 / 8,640（36.7%）的 query 上，
     两结果取并集能找回更多相关文档
      ↓
  ⭐ 这不是"理论上可能互补"，而是【实测确实高度不互补】
  ⭐ E2 的 RRF 融合有明确的量化依据
```

### ⚠️ 必须声明的局限

| # | 局限 | 对本结论的影响 |
|---|---|---|
| 1 | 语料仅 10 万段（全量 890 万） | 稠密检索的规模优势可能被低估；BM25 在小语料上相对更强 |
| 2 | dev 正例保证在库内 | 绝对指标偏高，**不可与 test 横比** |
| 3 | 稠密用 GPU、BM25 用 CPU | ✅ 已补 CPU 实测（`results/*_fair_cost_dev.json`）；⚠️ 延迟数字必须标批大小，见 [docs/05 §7.3](05-评测协议.md) |
| 4 | BGE max_length=512 tokens | 长段落（最长 87,586 字）被截断，稠密可能吃亏 |
| 5 | test 是 C-MTEB 采样版 | 不与论文全量指标直接比 |

> 尽管有上述局限，**"稠密显著优于 BM25"这个方向性结论是稳健的**：
> 差距 +38.2% 远超任何单一局限可能造成的偏差，且效应量达到"中等"级别。
> 但**具体数值**（如 0.7332）不能外推到其他语料规模。
