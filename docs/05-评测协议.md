## 一、为什么先写评测协议

```
⚠️ 一个常见的失败模式：

  先跑实验 → 看到数字 → 挑好看的报出来
        ↓
  ⭐ 这是【没有协议】的做法
     结果无法证伪、无法对比、无法复现

⭐ 正确顺序：

  先定义"什么算好" → 再跑实验 → 如实报告
        ↓
  所有指标【跑之前就定好】，跑完不许改
```

> 🔗 **这与 Course 2 第 13.1 节"建立单一评估指标"完全一致**：
> **"先定指标，再优化"是机器学习工程的第一原则。**

## 二、任务定义

### 2.1 检索任务的输入输出

```
输入：一个查询 query
      （如"南昌大学有哪些重点学科？"）

输出：一个【排序后的文档列表】
      [doc_1, doc_2, ..., doc_K]
        ↑
      按相关性从高到低排列

真值：数据集提供的【标注】
      (query, passage, label)
      label ∈ {相关, 不相关} 或 {0, 1, 2, 3} 分级
```

### 2.2 ⚠️ 关键概念区分（最容易搞错）

| 概念 | 含义 | 本项目 |
|---|---|---|
| **Passage（段落）** | 检索的最小单元 | 一个文档片段（如 100–500 字） |
| **Corpus（语料库）** | 全部候选段落集合 | DuReader 的 890 万段落 |
| **Query（查询）** | 用户的检索请求 | 数据集的问题/关键词 |
| **Relevant（相关）** | 与查询相关的段落 | 由数据集 label 定义 |
| **K（截断位置）** | 只看排序前 K 个 | 常用 K ∈ {1, 5, 10, 20, 100} |

## 三、⭐ 核心指标定义

### 3.1 Recall@K（召回率 @ K）

**定义**：前 K 个结果中，覆盖了多少比例的相关文档。

$$\Large \text{Recall@}K = \frac{\left|\text{Top-}K \cap \text{Relevant}\right|}{\left|\text{Relevant}\right|}$$

**例子：**

```
假设某 query 共有 3 个相关段落：{A, B, C}
系统返回 Top-5 = [A, D, B, E, F]

命中情况：A ✅（第1位）、B ✅（第3位）、C ❌（没进前5）
    ↓
Recall@5 = 命中 2 个 / 总共 3 个 = 【0.667】

若返回 Top-10 = [A, D, B, E, F, G, H, C, ...]
    ↓
Recall@10 = 命中 3 个 / 总共 3 个 = 【1.0】✅
```

**⭐ 适用场景**：**召回阶段的主指标**——关心"有没有漏掉"。

> 🔗 **对应 Course 3 第 123 P**：*"召回步骤的目标是确保广泛的覆盖……包含很多用户不太可能喜欢的物品是可以的。"*

---

### 3.2 Precision@K（精确率 @ K）

$$\Large \text{Precision@}K = \frac{\left|\text{Top-}K \cap \text{Relevant}\right|}{K}$$

**用上面的例子：**
```
Top-5 = [A, D, B, E, F]，命中 2 个
Precision@5 = 2 / 5 = 【0.4】
```

**⭐ 适用场景**：关心"返回的东西有多少是垃圾"。

> ⚠️ **注意**：检索任务里 **Recall@K 通常比 Precision@K 更重要**——因为检索是"粗筛"，后面还有重排序。

---

### 3.3 MRR@K（平均倒数排名）

**定义**：**第一个**相关文档的排名的倒数，对所有 query 取平均。

$$\Large \text{MRR@}K = \frac{1}{|Q|}\sum_{q=1}^{|Q|}\frac{1}{\text{rank}_q}$$

**例子：**

```
Query 1：第一个相关文档在第 3 位  → 1/3 = 0.333
Query 2：第一个相关文档在第 1 位  → 1/1 = 1.000
Query 3：第一个相关文档在第 10 位 → 1/10 = 0.100

MRR@10 = (0.333 + 1.000 + 0.100) / 3 = 【0.478】
```

**⭐ 特点**：**只看第一个命中的位置**——衡量"用户多快能看到有用结果"。

**⚠️ 局限**：忽略后续相关文档。如果有 5 个相关文档但第一个在第 9 位，MRR 会很差，即使后面都命中了。

---

### 3.4 nDCG@K（归一化折损累计增益）⭐⭐

**这是检索任务的"综合最优指标"，也是与论文对比时的标准。**

#### 第 1 步：DCG（折损累计增益）

$$\Large \text{DCG@}K = \sum_{i=1}^{K}\frac{2^{rel_i} - 1}{\log_2(i+1)}$$

| 部分 | 含义 |
|---|---|
| $rel_i$ | 第 $i$ 位的相关度（0/1 或 0–3 分级） |
| $2^{rel_i} - 1$ | **增益**：相关度越高，增益越大（分级标注时用） |
| $\log_2(i+1)$ | ⭐ **折损**：排名越靠后，除数越大，贡献越小 |

**⭐ 折损的直观含义：**

```
   位置 1：÷ log₂(2) = ÷ 1.00   ← 权重 1.000
   位置 2：÷ log₂(3) = ÷ 1.58   ← 权重 0.631
   位置 3：÷ log₂(4) = ÷ 2.00   ← 权重 0.500
   位置 4：÷ log₂(5) = ÷ 2.32   ← 权重 0.431
   位置 5：÷ log₂(6) = ÷ 2.58   ← 权重 0.387
        ↓
   ⭐ 排在第 1 位的贡献 ≈ 第 3 位的 2 倍
      这就是为什么"排序"如此重要
```

#### 第 2 步：IDCG（理想 DCG）

**把相关文档按"最理想顺序"排列后算出的 DCG**（即全部相关文档排在前面）。

#### 第 3 步：nDCG

$$\Large \text{nDCG@}K = \frac{\text{DCG@}K}{\text{IDCG@}K} \in [0, 1]$$

**⭐ 为什么要归一化？** 因为不同 query 的相关文档数量不同——归一化后才能跨 query 平均。

**完整例子：**

```
某 query 有 3 个相关段落，系统返回 Top-5 的 label 为：
    位置:  1   2   3   4   5
    label: 1   0   1   0   1

【DCG@5】
    = (2¹−1)/log₂(2) + (2⁰−1)/log₂(3) + (2¹−1)/log₂(4)
      + (2⁰−1)/log₂(5) + (2¹−1)/log₂(6)
    = 1/1.000 + 0/1.585 + 1/2.000 + 0/2.322 + 1/2.585
    = 1.000 + 0 + 0.500 + 0 + 0.387
    = 【1.887】

【IDCG@5】（理想顺序：1,1,1,0,0）
    = 1/1.000 + 1/1.585 + 1/2.000 + 0 + 0
    = 【1.631】
    ⚠️ 等等，这里 DCG > IDCG 了，说明算错了

【⚠️ 修正说明】
    上面例子中 label 序列是 [1,0,1,0,1]，共 3 个相关
    IDCG 应该把 3 个 1 放在最前： [1,1,1,0,0]
    = 1/1.000 + 1/1.585 + 1/2.000 = 1.631

    但 DCG 算出 1.887 > 1.631 ← ⚠️ 不可能！

    ⭐ 原因：DCG 的 label 序列算错了。
    [1,0,1,0,1] 的 DCG：
        位1: (2¹−1)/log₂(2) = 1/1.000 = 1.000
        位2: (2⁰−1)/log₂(3) = 0/1.585 = 0
        位3: (2¹−1)/log₂(4) = 1/2.000 = 0.500
        位4: (2⁰−1)/log₂(5) = 0/2.322 = 0
        位5: (2¹−1)/log₂(6) = 1/2.585 = 0.387
        合计 = 1.887

    IDCG 用同样 3 个相关：[1,1,1,0,0]
        位1: 1/1.000 = 1.000
        位2: 1/1.585 = 0.631
        位3: 1/2.000 = 0.500
        合计 = 2.131  ← ⭐ 正确的 IDCG

    nDCG@5 = 1.887 / 2.131 = 【0.886】
```

> ⚠️ **上面这段"自我纠错"是故意保留的**——它演示了一个真实陷阱：
> **IDCG 必须由【同一组 label 的最优排序】算出，容易算错。**
> **⭐ 实现时必须加断言：`DCG <= IDCG + 1e-9`，否则说明代码有 bug。**

### 3.5 ⭐ 三个指标的分工

| 指标 | 关心什么 | 适用阶段 | 对本项目的意义 |
|---|---|---|---|
| **Recall@K** | 有没有漏掉 | ⭐ **召回阶段** | 衡量"候选集够不够全" |
| **MRR@K** | 多快看到第一个有用的 | 排序阶段 | 衡量"用户首次满意度" |
| **nDCG@K** | ⭐ **整体排序质量** | ⭐ **重排序阶段** | ⭐ **主指标** |

**⭐ 本项目的指标使用约定：**

```
E1（基线对比）：  主看 Recall@10、nDCG@10
E2（混合检索）：  主看 nDCG@10
E3（重排序）：    ⭐ 主看 nDCG@10（因为重排序不改召回，只改顺序）
E4（分块消融）：  主看 Recall@10
```

## 四、⚠️ 五个常见错误（务必避免）

### 错误 1：把 Recall 和 Precision 搞反

```
❌ 错误说法："我们的召回率是 95%，说明结果很准"
    ⚠️ 召回率高 ≠ 准！召回率高只说明"没漏掉"
        （极端情况：返回全部 890 万段落，Recall=100%，但 Precision≈0）

✅ 正确理解：
    召回率 → 漏不漏
    精确率 → 准不准
    两者【必须一起报】
```

### 错误 2：K 值不一致

```
❌ 错误：A 方法报 Recall@100，B 方法报 Recall@10
        然后说"A 比 B 好"

✅ 正确：所有方法【必须用同一个 K】
        且要报告【多个 K】看趋势
        （如 Recall@1, @5, @10, @20, @100）
```

### 错误 3：⭐ 测试集泄漏

```
❌ 错误：用测试集调参（"试了几个配置，选测试集最好的那个"）
    ⚠️ 这会让指标虚高，无法反映真实泛化能力

✅ 正确：
    · 训练/验证集调参
    · ⭐ 测试集【只跑一次】并报告
```

> 🔗 **这与 Course 3 第 111 P 讲的"ε 必须在 CV 集上选，测试集只用来报告"完全同构。**

### 错误 4：忽略了"多相关标注"

```
⚠️ DuReader-retrieval 某些 query 可能有【多个】相关段落
    → 如果只算第一个命中的位置，会低估系统能力

✅ 正确：用 Recall@K（覆盖多个）或 nDCG@K（综合考虑）
```

### 错误 5：⭐ 平均值 vs 中位数

```
⚠️ 如果某些 query 一个相关文档都没有（数据脏），
   指标会出现 NaN 或 0，把平均值拉低

✅ 正确做法：
    · 过滤掉无相关文档的 query（并在文档中说明过滤了多少）
    · ⭐ 同时报告【平均值】和【中位数】
```

## 五、评测流程（标准操作程序）

```
┌──────────────────────────────────────────────────────────┐
│  Step 1  数据划分（⭐ 跑实验【之前】就要定好）              │
│          · test 集：数据集官方划分，【锁死不动】            │
│          · dev 集：从 train 里切 10%，用于调参              │
├──────────────────────────────────────────────────────────┤
│  Step 2  建立基线                                          │
│          · ⭐ 必须先从【最简单的 BM25】开始                 │
│          · 基线跑通 = 评测脚本正确 ✅                       │
├──────────────────────────────────────────────────────────┤
│  Step 3  运行实验（E1 → E2 → E3 → E4）                     │
│          · 每次只改【一个变量】                             │
├──────────────────────────────────────────────────────────┤
│  Step 4  记录结果                                          │
│          · ⭐ 写入 results/ 下的 CSV/JSON                   │
│          · 同时记录【配置参数】（保证可复现）               │
├──────────────────────────────────────────────────────────┤
│  Step 5  显著性检验（⭐ 进阶要求）                          │
│          · 提升 < 1% 时，要做显著性检验判断是否为噪声       │
└──────────────────────────────────────────────────────────┘
```

## 六、⭐ 显著性检验（避免"把噪声当提升"）

**⚠️ 问题**：nDCG 从 0.412 提升到 0.418（+0.006）——这是真提升还是随机波动？

**做法：配对 t 检验（paired t-test）或 bootstrap 置信区间**

```python
# 概念示例（不是可直接运行的完整代码）
import numpy as np
from scipy import stats

# 两个方法在【每个 query】上的 nDCG 分数
ndcg_method_a = np.array([...])   # 长度 = query 数
ndcg_method_b = np.array([...])

# 配对 t 检验
t_stat, p_value = stats.ttest_rel(ndcg_method_b, ndcg_method_a)

if p_value < 0.05:
    print(f"✅ 提升显著（p={p_value:.4f}）")
else:
    print(f"⚠️ 提升不显著（p={p_value:.4f}），可能是噪声")
```

**⭐ 报告规范：**

| 情况 | 怎么报 |
|---|---|
| p < 0.05 | "提升 **显著**（+X%，p<0.05）" |
| p ≥ 0.05 | ⭐ "提升 **不显著**（+X%，p=0.XX）——**可能是噪声**" |

> 🎯 **这一条能显著提升项目的专业度**——**大多数学生项目只报数字，不做显著性检验。**

## 八、与论文对比的注意事项

**⭐ 如果你想把自己的数字和论文比：**

| 注意点 | 说明 |
|---|---|
| **语料库规模必须一致** | ⚠️ 10 万段落 vs 890 万段落，指标不可比 |
| **评测集必须一致** | 不同 test set 指标不可比 |
| **K 值必须一致** | 论文报 Recall@100，你别报 Recall@10 |
| **指标定义可能不同** | ⚠️ 有些论文的 MRR 定义有细微差异 |

**⭐ 建议做法：**

```
第一步：先在【论文的完整设置】下复现，确认能对上
        ↓
   能对上 → 说明你的评测脚本正确 ✅ → 再做自己的实验
   对不上 → ⚠️ 先查 bug，别急着改模型
```

## 十、实现参考

**⭐ 指标实现的注意事项：**

```python
def recall_at_k(ranked_ids, relevant_ids, k):
    """Recall@K。

    ⚠️ 注意：如果 relevant_ids 为空，应返回 None（而非 0），
        并在统计时过滤掉，否则会拉低平均值。
    """
    if not relevant_ids:
        return None
    top_k = set(ranked_ids[:k])
    return len(top_k & set(relevant_ids)) / len(relevant_ids)


def ndcg_at_k(ranked_ids, relevant_ids, k):
    """nDCG@K。

    ⚠️ 必须断言 DCG <= IDCG，否则说明实现有 bug。
    """
    import math

    def dcg(ids):
        return sum(
            (1.0 / math.log2(i + 2))       # 位 i（0-based）的折损
            for i, doc in enumerate(ids[:k])
            if doc in relevant_ids
        )

    actual = dcg(ranked_ids)
    # IDCG：理想情况是把所有相关文档排在最前面
    ideal_ids = list(relevant_ids) + [None] * k
    ideal = dcg(ideal_ids)

    assert actual <= ideal + 1e-9, (
        f"⚠️ DCG({actual}) 不应大于 IDCG({ideal})，实现有 bug"
    )
    return actual / ideal if ideal > 0 else 0.0
```

> ⚠️ **上面的代码是骨架**，实际实现时参考标准库（如 `pytrec_eval`、`ranx`）并做单元测试验证。
