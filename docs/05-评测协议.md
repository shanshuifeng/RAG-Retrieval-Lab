## 一、为什么先定义评测协议

一种常见的失败模式是：先运行实验，再根据看到的数字挑选有利的结果来报告。这种做法没有协议，其结果无法证伪、无法对比、也无法复现。

正确顺序是：先定义"什么算好"，再运行实验，然后如实报告。所有指标在实验开始前确定，实验结束后不得修改。

这与 Course 2 第 13.1 节"建立单一评估指标"的原则一致：先定指标，再优化。

## 二、任务定义

### 2.1 检索任务的输入与输出

- 输入：一个查询 query（例如"南昌大学有哪些重点学科？"）
- 输出：一个按相关性从高到低排序的文档列表 `[doc_1, doc_2, ..., doc_K]`
- 真值：数据集提供的标注 `(query, passage, label)`，其中 `label ∈ {相关, 不相关}` 或 `{0, 1, 2, 3}` 分级

### 2.2 关键概念区分

| 概念 | 含义 | 本项目 |
|---|---|---|
| Passage（段落） | 检索的最小单元 | 一个文档片段（约 100–500 字） |
| Corpus（语料库） | 全部候选段落集合 | DuReader 的 890 万段落 |
| Query（查询） | 用户的检索请求 | 数据集的问题或关键词 |
| Relevant（相关） | 与查询相关的段落 | 由数据集 label 定义 |
| K（截断位置） | 只看排序前 K 个 | 常用 K ∈ {1, 5, 10, 20, 100} |

## 三、核心指标定义

### 3.1 Recall@K（召回率）

前 K 个结果覆盖了多少比例的相关文档：

$$\text{Recall@}K = \frac{\left|\text{Top-}K \cap \text{Relevant}\right|}{\left|\text{Relevant}\right|}$$

示例：某 query 共有 3 个相关段落 {A, B, C}，系统返回 Top-5 = [A, D, B, E, F]。

- A 在第 1 位命中，B 在第 3 位命中，C 未进入前 5
- Recall@5 = 2 / 3 = 0.667

适用场景：召回阶段的主指标，衡量"是否遗漏"。

> 对应 Course 3 第 123 页：召回步骤的目标是确保广泛的覆盖，包含用户不太可能喜欢的条目是可以接受的。

### 3.2 Precision@K（精确率）

$$\text{Precision@}K = \frac{\left|\text{Top-}K \cap \text{Relevant}\right|}{K}$$

沿用上例：Top-5 命中 2 个，Precision@5 = 2 / 5 = 0.4。

在检索任务中，Recall@K 通常比 Precision@K 更重要，因为检索是粗筛阶段，之后还有重排序。

### 3.3 MRR@K（平均倒数排名）

第一个相关文档排名的倒数，对所有 query 取平均：

$$\text{MRR@}K = \frac{1}{|Q|}\sum_{q=1}^{|Q|}\frac{1}{\text{rank}_q}$$

示例：三个 query 的第一个相关文档分别在第 3、1、10 位，则

MRR@10 = (1/3 + 1/1 + 1/10) / 3 = 0.478

MRR 只看第一个命中的位置，衡量用户多快看到第一个有用结果。其局限在于忽略后续相关文档：若有 5 个相关文档但第一个在第 9 位，MRR 会很低，即使其余都命中。

### 3.4 nDCG@K（归一化折损累计增益）

这是检索任务的综合指标，也是与论文对比时的标准。

第一步，计算 DCG：

$$\text{DCG@}K = \sum_{i=1}^{K}\frac{2^{rel_i} - 1}{\log_2(i+1)}$$

其中 $rel_i$ 为第 $i$ 位的相关度，$2^{rel_i}-1$ 为增益（相关度越高增益越大），$\log_2(i+1)$ 为位置折损（排名越靠后贡献越小）。

位置折损的直观含义：

- 位置 1：权重 1.000
- 位置 2：权重 0.631
- 位置 3：权重 0.500
- 位置 4：权重 0.431
- 位置 5：权重 0.387

第 1 位的贡献约为第 3 位的 2 倍，这正是排序如此重要的原因。

第二步，计算 IDCG（理想 DCG），即将相关文档按最优顺序排列后算出的 DCG。

第三步，归一化：

$$\text{nDCG@}K = \frac{\text{DCG@}K}{\text{IDCG@}K} \in [0, 1]$$

归一化的必要性在于不同 query 的相关文档数量不同，归一化后才能跨 query 平均。

完整计算示例：某 query 有 3 个相关段落，系统返回 Top-5 的 label 序列为 [1, 0, 1, 0, 1]。

```
DCG@5 = 1/log2(2) + 0 + 1/log2(4) + 0 + 1/log2(6)
      = 1.000 + 0 + 0.500 + 0 + 0.387
      = 1.887

IDCG@5（理想序列 [1, 1, 1, 0, 0]）
      = 1/log2(2) + 1/log2(3) + 1/log2(4)
      = 1.000 + 0.631 + 0.500
      = 2.131

nDCG@5 = 1.887 / 2.131 = 0.886
```

注意：IDCG 必须由同一组 label 的最优排序算出。实现时必须断言 `DCG <= IDCG + 1e-9`，否则说明代码存在缺陷。

### 3.5 三个指标的分工

| 指标 | 关注点 | 适用阶段 | 对本项目的意义 |
|---|---|---|---|
| Recall@K | 是否遗漏 | 召回阶段 | 衡量候选集是否足够全 |
| MRR@K | 多快看到第一个有用结果 | 排序阶段 | 衡量首次命中满意度 |
| nDCG@K | 整体排序质量 | 重排序阶段 | 主指标 |

本项目的指标约定：

- E1（基线对比）：主看 Recall@10、nDCG@10
- E2（混合检索）：主看 nDCG@10
- E3（重排序）：主看 nDCG@10（重排不改召回，只改顺序）
- E4（分块消融）：主看 Recall@10

## 四、五个常见错误

### 错误 1：混淆 Recall 与 Precision

"召回率 95%" 只说明没有遗漏，不代表结果准确。极端情况下，返回全部 890 万段落时 Recall=100%，但 Precision 接近 0。

召回率回答"漏不漏"，精确率回答"准不准"，两者应同时报告。

### 错误 2：K 值不一致

不同方法使用不同 K 值进行比较是错误的。所有方法必须使用同一个 K，并报告多个 K 以观察趋势（如 Recall@1, @5, @10, @20, @100）。

### 错误 3：测试集泄漏

用测试集调参会使指标虚高，无法反映真实泛化能力。正确做法是在验证集上调参，测试集只运行一次并报告。

> 这与 Course 3 第 111 页"ε 必须在 CV 集上选择，测试集只用来报告"的原则一致。

### 错误 4：忽略多相关标注

DuReader-retrieval 的某些 query 可能有多个相关段落。若只统计第一个命中位置，会低估系统能力。应使用 Recall@K 或 nDCG@K。

### 错误 5：平均值与中位数

若某些 query 没有任何相关文档（数据噪声），指标会出现 NaN 或 0，拉低平均值。正确做法是过滤无相关文档的 query（并说明过滤数量），同时报告平均值和中位数。

## 五、评测流程

```
Step 1  数据划分（在实验前确定）
        - test 集：官方划分，锁死不动
        - dev 集：从 train 切分，用于调参

Step 2  建立基线
        - 从最简单的 BM25 开始
        - 基线跑通即说明评测脚本正确

Step 3  运行实验（E1 → E2 → E3 → E4）
        - 每次只改一个变量

Step 4  记录结果
        - 写入 results/ 下的 JSON
        - 同时记录配置参数，保证可复现

Step 5  显著性检验
        - 提升幅度较小时，需判断是否为噪声
```

## 六、显著性检验

nDCG 从 0.412 提升到 0.418（+0.006），这是真实提升还是随机波动？通过配对 t 检验或 bootstrap 置信区间判断。

```python
import numpy as np
from scipy import stats

# 两个方法在每个 query 上的 nDCG 分数
ndcg_method_a = np.array([...])
ndcg_method_b = np.array([...])

t_stat, p_value = stats.ttest_rel(ndcg_method_b, ndcg_method_a)

if p_value < 0.05:
    print(f"提升显著（p={p_value:.4f}）")
else:
    print(f"提升不显著（p={p_value:.4f}），可能是噪声")
```

报告规范：

| 情况 | 表述 |
|---|---|
| p < 0.05 | 提升显著（+X%，p<0.05） |
| p ≥ 0.05 | 提升不显著（+X%，p=0.XX），可能是噪声 |

### 7.2 必须记录失败的配置

记录失败的实验比记录成功的更有价值：他人会踩同样的坑，负面结果最能说明边界所在。

### 7.3 成本（延迟）如何报告才不误导

每个延迟数字必须同时标注三个维度：

- batch_size：一次编码多少条 query
- device：cpu / cuda，以及 dtype（fp32 / fp16）
- 包含内容：只算检索，还是含 query 编码或重排

三种口径的实测差异（2026-10-31，`scripts/measure_fair_cost.py`）：

| 口径 | batch | 方法 | 设备 | ms/query |
|---|---|---|---|---|
| 单 query（线上真实延迟） | 1 | BM25(调优) | cpu | 0.627 |
| 单 query | 1 | dense/base | cuda · fp32 | 91.9 |
| 单 query | 1 | dense/base | cpu · fp32 | 152.2 |
| 批量摊销（离线吞吐） | 300 | dense/base | cuda · fp32 | 4.50 |
| 批量摊销 | 300 | dense/base | cpu · fp32 | 28.1 |

同一方法在单条与批量口径下差异显著（GPU 差 20.4 倍，CPU 差 5.4 倍）。用 batch 口径估算线上延迟，会把成本低估一个数量级以上。

绝对值不可跨天比较：同一 batch=300 口径下，2026-10-25 测得 0.706 ms/q，2026-10-31 测得 4.50 ms/q，相差 6.4 倍，原因未定位（环境：torch 2.14.1+cu130，GPU 时钟 2370/3105 MHz）。两次测量都保留了原始 JSON，但只有同一次运行内的倍数关系是可靠的。

因此本项目的纪律是：跨方法比较使用同一次运行内的倍数，绝对延迟只在同一文档内报告，且必须带 batch/device/dtype 三个标签。

## 八、与论文对比的注意事项

| 注意点 | 说明 |
|---|---|
| 语料库规模必须一致 | 10 万段落与 890 万段落的指标不可比 |
| 评测集必须一致 | 不同 test set 的指标不可比 |
| K 值必须一致 | 论文报 Recall@100 时不应报 Recall@10 |
| 指标定义可能不同 | 部分论文的 MRR 定义存在细微差异 |

建议做法：先在论文的完整设置下复现，确认指标一致后再开展自己的实验。能对上说明评测脚本正确，对不上则先排查缺陷，而非急于调整模型。

## 十、实现参考

```python
def recall_at_k(ranked_ids, relevant_ids, k):
    """Recall@K。

    若 relevant_ids 为空，返回 None（而非 0），
    并在统计时过滤，否则会拉低平均值。
    """
    if not relevant_ids:
        return None
    top_k = set(ranked_ids[:k])
    return len(top_k & set(relevant_ids)) / len(relevant_ids)


def ndcg_at_k(ranked_ids, relevant_ids, k):
    """nDCG@K。

    必须断言 DCG <= IDCG，否则说明实现有缺陷。
    """
    import math

    def dcg(ids):
        return sum(
            (1.0 / math.log2(i + 2))
            for i, doc in enumerate(ids[:k])
            if doc in relevant_ids
        )

    actual = dcg(ranked_ids)
    ideal_ids = list(relevant_ids) + [None] * k
    ideal = dcg(ideal_ids)

    assert actual <= ideal + 1e-9, (
        f"DCG({actual}) 不应大于 IDCG({ideal})，实现有缺陷"
    )
    return actual / ideal if ideal > 0 else 0.0
```

上述代码为骨架，实际实现时应参考标准库（如 `pytrec_eval`、`ranx`）并做单元测试验证。
