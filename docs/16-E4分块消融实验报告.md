## 零、⭐ 本报告要回答什么

> **Q4：文档怎么切最好？**

**答案：在本数据集上，怎么切都不如不切。**

这不是我预期的结果——分块通常被认为能提升检索（缓解长文档的信息稀释、适配模型 512 token 上限）。但实测数据不允许我说它有效。

---

## 一、⭐ 为什么做这个实验

数据里有一个明显的"可疑信号"：

```
E1 的质检发现（data/DATACARD.md §2.1）：
   段落长度    min=1 字，中位 283 字，P95 797 字
   最长段落    87,586 字（dev 数据集）
   > 1000 字   3,355 段（3.4%）
   > 5000 字   70 段
        ↓
两个理论上的担忧：
  ① 长段落信息稀释 → 检索时关键句被淹没
  ② 稠密模型 max_length=512 tokens → 长段落被硬截断，尾部信息丢失
        ↓
预期：分块应该能改善，尤其是对稠密检索
```

---

## 二、实验设置

### 2.1 策略（docs/04 §4.2）

| 策略 | 做法 | 块数变化 |
|---|---|---|
| **A. native** | 不切分（原生 passage，E1–E3 的基线） | 100,000 |
| **B. fixed256** | 固定 256 字 + 重叠 50 字 | **211,852**（2.12 块/段） |
| **C. fixed512** | 固定 512 字 + 重叠 50 字 | 120,007（1.20 块/段） |
| **D. paragraph** | 按 `\n\n` 切，超长段落再按 512 兜底 | 120,033（1.20 块/段） |

### 2.2 ⭐ 评测口径（这是本实验最容易错的地方）

```
分块后，检索单位是「块」，但 qrels 标注的是「段落」。
        ↓
判定规则（本项目采用）：
  · 块 id 形如 {pid}#c{序号}
  · 块级排名 → 投影回段落级：任一 chunk 命中 = 父段落召回
  · 同一父段落的多个块在投影后只占【一个】位置（去重保序）
  · 投影后再用段落级 qrels 算指标
        ↓
⚠️ 若不做投影、或投影错位，指标会【系统性偏高或偏低】，且不报错。
   该逻辑有 18 项独立单测保障（tests/test_chunking.py），
   含「双向映射互逆」「去重」「未知块报错」等检查。
```

### 2.3 检索器

两种都测（避免"分块只对某种检索器有效"的结论偏差）：
- **BM25**（k1=0.7, b=0.75，E1 锁定）
- **D2 / BGE-base**（无指令，fp16，E1 复核锁定）

---

## 三、⭐ 结果：全部显著变差

### 3.1 BM25

| 策略 | Recall@10 | nDCG@10 | vs native | p 值 | 块数 |
|---|---|---|---|---|---|
| **native** | **0.6102** | **0.5305** | — | — | 100,000 |
| fixed256 | 0.6014 | 0.5218 | **-1.66%** | 1.6e-14 | 211,852 |
| fixed512 | 0.6087 | 0.5276 | **-0.55%** | 1.2e-06 | 120,007 |
| paragraph | 0.6086 | 0.5277 | **-0.54%** | 1.9e-06 | 120,033 |

### 3.2 D2 / BGE-base 稠密

| 策略 | Recall@10 | nDCG@10 | vs native | p 值 | 块数 |
|---|---|---|---|---|---|
| **native** | **0.8875** | **0.8139** | — | — | 100,000 |
| fixed256 | 0.8703 | 0.7929 | **-2.58%** | 1.5e-68 | 211,852 |
| fixed512 | 0.8845 | 0.8112 | **-0.33%** | 3.5e-07 | 120,007 |
| paragraph | 0.8844 | 0.8111 | **-0.34%** | 1.2e-07 | 120,033 |

### 3.3 ⭐ 规律：块越小越差

```
BM25:    fixed256 (-1.66%)  <  fixed512 (-0.55%) ≈ paragraph (-0.54%)
稠密:    fixed256 (-2.58%)  <  fixed512 (-0.33%) ≈ paragraph (-0.34%)
                                                    ↑
                    越小越碎 → 越差；越大越接近 native → 越接近基线
```

**这说明：分块的损害与"切碎程度"正相关**。fixed512 和 paragraph 的块数几乎相同（1.2 块/段），结果也几乎相同，互为交叉验证。

## 四、⭐ 为什么分块反而变差？——机理分析

### 原因 ①：截断担忧被高估了

我原以为"max_length=512 tokens 会截断长段落"。但实测：

```
段落长度中位 283 字，P95 797 字
字数 → token 数大致 1:1.2（中文）
        ↓
P95 段落约 950 tokens —— 确实会被截断
        ↓
但只有 3.4% 的段落 > 1000 字，而这部分段落【很少有相关标注】
（qrels 9,792 个相关段落中，长段落占比更低）
        ↓
⭐ 截断损害只影响极少数 query，而分块对所有 query 都引入新问题
```

### 原因 ②：段落本身就是"语义完整单元"

```
DuReader 的 passage 来自网页的【段落级】抽取，本身就是语义连贯的单元。
        ↓
按 256/512 字硬切 → 把一个完整意思切成两半
        ↓
⭐ 块内出现"有主语没谓语"或"有结论没前提"的碎片
   → 检索信号被破坏，而不仅仅是"变短"
```

### 原因 ③：段落级投影的"位置稀释"

```
投影规则：同一父段落的多个块，投影后只占一个位置
        ↓
块级 top-10 如果被 2 个块占满（同一段落），投影后只剩 1 个位置
   → 有效候选变少，@10 的召回空间被压缩
        ↓
这是分块范式在【段落级评测】下的结构性劣势。
   ⚠️ 注意：若评测口径改为"块级相关"（标注到块），此劣势会消失。
   但本数据集只有段落级标注，无法做块级评测。
```

**⭐ 第 ③ 点是最重要的方法论发现**：
不是"分块无用"，而是"**在段落级标注 + 段落级评测下，分块有结构性劣势**"。

## 五、⭐ 结论（Q4 的答案）

| 问题 | 答案 |
|---|---|
| 分块能提升检索吗？ | ❌ **不能**，三种策略均显著变差（-0.33% ~ -2.58%） |
| 哪种分块最好？ | fixed512 ≈ paragraph（-0.33%），最接近不切分；**但仍不如不切分** |
| 块越小越好还是越大越好？ | **越大越接近 native 越好**，越小越差 |
| 分块完全无用吗？ | ⚠️ **不能这么说**。见下方边界 |

### ⚠️ 本结论的有效边界（三条缺一不可）

```
① 数据：DuReader 的 passage 本身已是段落级语义单元。
        若原始文档是【整篇网页】（数万字），分块仍是必要的。

② 评测口径：本实验是【块级检索 → 投影回段落级评测】。
        该口径下分块有「位置稀释」劣势。
        若有块级标注（qrels 标到块），结论可能反转。

③ 任务：本任务是 short-query → passage 检索。
        若是长文档问答（需要定位到具体句子），分块可能更优。
```

> ⭐ 引用本结论时必须带这三条边界，否则会被误读为"分块无用论"。

## 六、成本

| 策略 | 块数 | BM25 建索引 | 稠密编码 |
|---|---|---|---|
| native | 100,000 | 75s | 231s |
| fixed256 | 211,852 | 84s | **347s** |
| fixed512 | 120,007 | 75s | 311s |
| paragraph | 120,033 | 75s | 317s |

> 分块不仅效果更差，成本还更高（块数翻倍 → 索引/编码时间增加）。
