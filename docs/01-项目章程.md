## 一、一句话定义

用可复现的方式，量化中文检索增强生成（RAG）中每个环节对最终效果的真实贡献。

## 三、项目目标

### 3.1 主要目标（必须达成）

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | 建立可复现的中文检索评测基线 | 在 DuReader-retrieval 上跑出 Recall@10 / MRR@10 / nDCG@10 |
| G2 | 对比至少 3 种检索方案 | BM25（稀疏）、稠密向量、混合检索各跑通并有数据 |
| G3 | 完成消融实验 | 量化重排序与分块策略的影响 |
| G4 | 产出可交付的实验报告 | 含图表、结论、局限说明 |

### 3.2 次要目标（加分项）

| # | 目标 |
|---|---|
| G5 | 对比不同嵌入模型（BGE-small / BGE-base / text2vec）的效果与成本权衡 |
| G6 | 接入 LLM 生成答案，评测端到端 QA 效果（含引用准确性） |
| G7 | 用 LLM-as-Judge 做评测，并与人工标注对比一致性 |

### 3.3 明确不做（范围边界）

不做大模型预训练，不做大模型全参微调（8GB 显存不够），不做分布式或大规模工程化部署，不做前端界面（本项目是实验台而非产品）。

---

## 四、核心研究问题

一个问题驱动整个项目：

> 在中文检索任务上，从 BM25 基线到混合检索 + 重排序，每一层能带来多少真实提升？这些提升值不值得相应的计算成本？

拆解为四个子问题：

| # | 子问题 | 对应实验 |
|---|---|---|
| Q1 | 稠密向量比 BM25 好多少？ | E1 |
| Q2 | 混合检索（RRF 融合）比单一方法好吗？ | E2 |
| Q3 | 加一个 Cross-encoder 重排序值不值？ | E3 |
| Q4 | 文档分块策略对召回影响多大？ | E4 |

---

## 五、技术路线

```
查询 Query
   │
   ├─ BM25（稀疏索引）
   ├─ 稠密检索（向量 + FAISS）
   └─（扩展）多路召回
            │
            ▼
        融合（RRF / 加权）
            │
            ▼
        候选集 Top-K
            │
            ▼
        Cross-encoder 重排序
            │
            ▼
        最终 Top-N
            │
            ▼
      （可选）LLM 生成

每个箭头处，都是本项目要量化的边际收益点
```

## 六、关键决策记录

| 决策项 | 选择 | 理由 |
|---|---|---|
| 数据集 | DuReader-retrieval | ModelScope 直连，无需翻墙，自带相关性标注 |
| 备选数据集 | T2Ranking / C-MTEB | 若主数据集有问题可切换 |
| 检索库 | FAISS（CPU 即可） | 8GB 显存够用，且不依赖 GPU |
| 嵌入模型 | BGE 系列（small / base） | 中文效果好、体积小、可本地跑 |
| 基线 | BM25 | 必须有强基线，否则无法证明向量检索的价值 |
| 评测指标 | Recall@k, MRR@k, nDCG@k | 检索任务标准指标 |
| 框架 | 纯 Python + numpy，不用 LangChain | 见下方说明 |

### 为什么不用 LangChain / LlamaIndex

本项目目标是量化每个环节的贡献，需要精确控制每一步。高层框架会把细节封装掉：看不到 BM25 的 k1/b 参数，看不到 RRF 的融合权重，调参与消融困难。因此选择手写核心逻辑，把框架作为可选项。

## 八、风险与应对

| # | 风险 | 概率 | 应对 |
|---|---|---|---|
| R1 | 数据集过大（890 万 passage）跑不动 | 高 | 先用子集（10 万 passage），验证流程后再全量 |
| R2 | 国内下载 HuggingFace 模型慢 | 中 | 用 ModelScope 镜像，或手动下载 |
| R3 | 8GB 显存不够 | 低 | 全部实验可用 CPU；BGE-small 约 100MB |
| R4 | 评测指标与论文对不上 | 中 | 先复现论文基线，确认评测脚本正确 |
| R5 | 工作量超预期 | 中 | 严格按 M0→M6 推进，每阶段可独立交付 |

## 九、学术诚信与局限声明

本项目从一开始就明确以下边界：

1. 用标准数据集与标准指标，不自定义"好看"的指标
2. 必须报告强基线（BM25），不允许只报自己方法的好结果
3. 负面结果也报告
4. 区分"数据集内表现"与"真实场景表现"，不外推
5. 本项目是学习实验，不是生产系统

技术结论必须诚实，包括对自己不利的结论。

---

## 十、成功标准

本项目算成功，如果：能回答"每层带来多少提升"且有数据支撑；评测脚本可复现；报告的局限说明比结论还充分。

本项目算失败，如果：只跑通 demo 而没有任何对比数据；只报最优结果而不报基线和负面结果；指标算错。
