**最重要的一条**：

## 一、🔴 严重缺陷

### S1：重排结论受"天花板效应"污染 —— ⭐ **已实测证实**

**原问题**：

```
test 集各方法的 nDCG@10：
  D2/BGE-base    0.8809  ← E3 的第一段
  D2+重排(K=20)  0.8823  ← 只提升 0.0016（+0.16%，不显著）

⭐ 0.8809 意味着理想上限只剩 11.9% —— 排序改进几乎没有空间
   项目把结果表述为「重排未复现」，容易被读成「重排无效」
```

**⭐ 审查补充实验（实测，`results/2026-10-25_215653_audit_rerank_firststage.json`）**：

把**同一个** cross-encoder 接在三档不同强度的第一段之后（dev，1,500 query，K=20）：

| 第一段 | 基线 nDCG@10 | 重排后 | 提升 | 相对 | 剩余空间 | 占剩余空间 | Cohen's d | p 值 |
|---|---|---|---|---|---|---|---|---|
| **BM25(调优)** | 0.5707 | 0.7017 | **+0.1309** | **+22.94%** | 42.9% | **30.5%** | **0.558** | 1.6e-90 |
| **D1/small** | 0.7474 | 0.8288 | **+0.0814** | **+10.88%** | 25.3% | **32.2%** | **0.409** | 2.4e-52 |
| **D2/base** | 0.8154 | 0.8542 | **+0.0388** | **+4.76%** | 18.5% | 21.0% | 0.215 | 1.8e-16 |

```
⭐ 惊人的单调关系：第一段越弱，重排提升越大
   BM25 (+22.94%) > D1 (+10.88%) > D2 (+4.76%)

⭐ 更有说服力的指标：提升占剩余空间的比例
   BM25: 30.5%  |  D1: 32.2%  |  D2: 21.0%
   → 前两档都在 30% 左右（重排能吃下三成的剩余空间）
   → D2 档掉到 21%（空间本身只剩 18.5%，绝对值太小，且已接近天花板）
```

**⚠️ 关键修正：项目原来的表述是错的**

| 原文表述 | 应改为 |
|---|---|
| "重排在 test 上不显著（+0.16%）→ **未复现**" | "重排在**强第一段（nDCG@10=0.88）**下无显著收益；<br>在弱第一段（BM25）下提升 **+22.94%（d=0.558，中效应）**" |

**为什么这是严重缺陷**：

```
一个读者看到「重排未复现」，会得出「重排不可靠」的判断
        ↓
但实测表明：重排【非常有效】，只是在 0.88 的第一段后面没有空间了
        ↓
⭐ 这是「结论表述错误」，不是「实验做错了」
   实验数据都是对的，但对数据的解读把「天花板效应」误读成了「方法失败」
```

**⚠️ 附带发现：这也影响 E3 的 K 甜点结论**

在 D2（强第一段）上 K=20 是最优（更大的 K 更差）。
但在弱第一段上，最优 K 可能不同（因为候选质量差，需要更多候选给重排选）。
**本审查未测这一点，应列为待办**。

**建议的修正**（已写入 P0 改进清单）：
1. 在 [docs/14](14-E3重排序实验报告.md)、[docs/15](15-test最终评测报告.md)、[docs/17](17-最终实验报告.md) 补充本节的对照表
2. 把"重排未复现"改为"强第一段下无空间；弱第一段下 +22.94%"
3. 重排的实践建议应改为：**"重排的价值取决于第一段强度——第一段越弱，重排越值得"**

## 二、🟠 中等缺陷

### M1：dev 集的构造方式引入了系统性偏差

**实测**（`data/processed/dev/stats.json`）：

```
dev 语料构造：
  · 22,280 个正例【全部】进入语料（100% 可召回保证）
  · 负例从 3,365,607 条池子里【随机】抽 77,720 条
```

**三个问题**：

| 问题 | 后果 |
|---|---|
| 正例全部在库 | dev 的召回率天然偏高，不存在"相关段落不在库中"的情况 |
| **负例是随机的** | 真实场景的"困难负例"是检索器捞出来的高相似段落；随机负例太容易区分 |
| 单一 seed（42） | 无法评估抽样噪声的影响 |

**量化影响**：

```
dev  BM25(调优) nDCG@10 = 0.5305（平均相关数 2.60）
test BM25(调优) nDCG@10 = 0.5680（平均相关数 4.92）

⭐ 同一方法在 test 上反而【更高】
   说明 test 虽然语料更真实，但"平均相关数多"的好处超过了"语料更难"的损失
   → 两个集的难度不可比，dev 上调出的参数不保证在 test 最优
```

**这是 dev/test 不对称的根本原因，比项目文档承认的"2.60 vs 4.92"更深一层。**

### M2：延迟测量用的是批量吞吐，但方向与我最初的判断不同（⭐ 已实测修正）

**我最初的判断（过于悲观，已修正）**：
> "E3 的 83ms/query 是离线吞吐，真实线上通常慢 2–5 倍"

**实测结果（`scripts/measure_real_latency.py`，50 query，单 query batch=1）**：

| 场景 | mean | P50 | P95 | P99 |
|---|---|---|---|---|
| 第一段检索（单 query） | **24.92 ms** | 25.43 | 26.64 | 27.58 |
| 重排 · 离线批量（E3 用的） | 74.59 ms | — | — | — |
| 重排 · 单 query | **75.48 ms** | 84.04 | 86.04 | 86.81 |
| **端到端（检索 + 重排）** | **100.34 ms** | 108.05 | 113.90 | 114.49 |

```
⭐ 关于重排：E3 估算 83ms vs 实测 75ms（0.91 倍）
   → ✅ E3 的重排延迟估算【基本准确】，我的"低估 2-5 倍"判断是错的
   → 原因：K=20 的 batch 太小（20 条），批处理摊销效果有限，
     所以离线吞吐与单 query 差距不大

⭐⭐ 但真正被严重低估的是【第一段检索】：
   E3 报告 0.84 ms/query（batch=256 的摊销口径）
   实测单 query 24.92 ms —— 差 30 倍
   → 原因：batch 时 256 条 query 一次编码，摊销后极快；
     单 query 时编码必须独占一次前向
```

**修正后的结论**：

| 项 | 项目原报告 | 实测修正 |
|---|---|---|
| 重排（K=20） | 83 ms（估算） | **75 ms**（实测，估算偏保守 10%） |
| 第一段检索 | 0.84 ms | **24.9 ms**（单 query） |
| **端到端** | 未报告 | **100 ms**（P95 114 ms） |

**影响**：
- E3 的成本结论（重排 83ms）**基本可用**，不需大改
- 但"检索快得几乎免费"这个印象是错的——单 query 检索要 25ms
- **项目此前从未报告过端到端延迟，这是缺失的关键数字**

**⚠️ 我的审查判断错误也记录在此**：M2 原判"低估 2-5 倍"是**基于直觉而非实测**，
实测证明重排估算准确。这正是审查报告本身也该被审查的例子。

### M3：缺少论文基线对照

**实测**：`docs/11` 至今写着"与文献对照：⏳ 待做"，`docs/17` 最终报告也未做。

**后果**：

```
无法回答：「我的 BM25 nDCG@10 = 0.5680 是否合理？」
        ↓
若实现有系统性偏差（分词、归一化、截断），【外部无从发现】
        ↓
项目内部的横向对比（稠密 vs BM25）依然有效，
但【绝对数值的可信度未经外部锚定】
```

**这是最容易被评审质疑的一点**：所有结论都建立在"指标实现正确"这个假设上，
而项目只验证了**内部一致性**（oracle/random/anti、独立重算），
没有验证**外部一致性**（与已发表结果同量级）。

### M4：E2 的结论被限制在单一组合上 —— ⭐ 已补测，且**项目自己的准则被证伪**

**我最初提出的问题**：
> E2 只测了 `BM25 × D2`（质量差 1.53×），并提出准则
> "当两方法质量悬殊时，RRF 融合是负优化"。
> 但项目**没测质量接近的组合**——而按它自己的准则，那时混合该有效。

**已补测（`scripts/run_e2b_close_quality.py`，dev）**：

| 组合 | 质量比 | Top-10 IoU | 最强单方法 | 最优混合 | 相对 | 混合有效？ |
|---|---|---|---|---|---|---|
| BM25 × D1 | 1.382 | 0.2143 | 0.7332 | 0.6882 | **-6.15%** | ❌ |
| BM25 × D2 | 1.534 | 0.2015 | 0.8139 | 0.7347 | **-9.73%** | ❌ |
| **D1 × D2** | **1.110（接近）** | 0.4136 | 0.8139 | 0.7906 | **-2.86%** | ❌ |

**⭐⭐ 结论：三个组合全部无效，包括质量只差 11% 的那组。**

```
⭐ 项目原准则「质量悬殊导致混合失败」——【被证伪】
   因为质量接近（1.110×）时混合依然下降。

⭐ 所有组合的最优 K 都落在最小档（5–10），且最优权重都是 w_弱 = 0
   → 这不是"参数没调好"，而是融合本身在这个设定下不该做。

⭐ 更可能的真实机理（新假设，需进一步验证）：
   RRF 按【排名】加权，无法识别"弱方法的第 1 名其实是错的"
   → 即使弱方法只弱 11%，它的 top 排名里仍有大量错误
   → 融合把这些错误排名拉进前列，稀释了强者的正确排序
   → 所以真正的门槛不是"质量差多少"，而是
     "弱方法的 top-10 里有多少是错的"（即 precision@10）

⭐ 重合度的作用（另一个观察）：
   D1×D2 的 IoU（0.414）比 BM25×D2（0.202）更高
   → 两方法越重合，融合能带来的【新信息】越少
   → 但 BM25×D2 IoU 更低却也是负优化
   → 说明"低重合"不是充分条件，还需"弱方法本身够好"
```

**这处修正对本项目结论的影响**：E2 的"混合负优化"结论**更强了**
（从单一组合扩展到三种，且排除了质量差这个干扰因素），
但项目原先给出的**机理解释是错的**，已在此修正。

### M5：统计方法的两个缺口

| 缺口 | 说明 |
|---|---|
| **未做多重比较校正** | E2 做了 10 组 k 网格 + 14 组权重扫描；E3 做了 4 组 K 网格。家族错误率被放大，未用 Bonferroni 或 FDR 校正（主结论效应量大，受影响有限，但应声明） |
| **单 seed 无重复** | 所有实验只跑一次。正确的做法是 3–5 个 seed，报告均值 ± 标准差。当前无法区分"方法差异"与"随机波动" |

## 三、🟡 轻微缺陷（工程质量）

### L1：实验脚本间大量重复代码

**实测**：

```
def paired_test(...) 出现在 5 个脚本里：
  run_e2_hybrid.py / run_e3_rerank.py / run_e4_chunking.py
  run_final_test.py / significance_test.py

评估逻辑（eval_method / per_q_ndcg）也重复了 5-6 处
```

**风险**：改一处忘另一处 → 各实验口径漂移。本项目已因"手抄数字"踩过坑（MRR 误抄）。

**建议**：抽出 `src/eval/experiment.py`，提供 `paired_test()`、`eval_run()`、`save_result()`。

### L2：缺少实验编排框架

12 个实验脚本各自实现"加载 run → 评测 → 检验 → 落盘"。
没有统一的实验注册/复现机制，导致：

- 复现步骤需要人工按 `docs/17 §九` 手动执行 10 步
- 无法一键重跑全部实验

### L3：文档冗余与陈旧内容风险

**实测**：

```
文档 17 份，共 123,808 字
  · docs/12（18,389 字）与 docs/09（6,804 字）里程碑信息重复
  · docs/11/13/14/16 与 docs/17 的指标大量重复
        ↓
⚠️ 重复 → 改一处忘另一处（已实际发生：docs/12 里 3 处旧数字残留）
```

**本次审查已修复**：docs/12 的 `0.7238`/`0.7936` 加上修正说明。

### L4：`bm25.py` 与 `bm25_fast.py` 并存但职责说明不足

快版用于生产、慢版仅作验证基准。这个设计**合理**（等价性验证的必要手段），
但模块文档没说清"为什么保留两份""何时该用哪个"，新人容易误用慢版。

### L5：`src/` 下的校验方法不统一

```
dense.py    : 无 assert 检查
bm25.py     : 无 assert 检查
cross_encoder.py : 有 assert
metrics.py  : 有硬断言（DCG<=IDCG）
```

**建议**：统一的输入校验（维度、空输入、NaN 检查）。

### L6：`results/` 里存在被覆盖的中间产物

**实测** `data/index/`：

```
rerank_scores_d2_dev_debug500q.json   2.4 MB  ← 500 条调试缓存，已被 8640q 取代
bm25_dev_k11.5_b0.75.pkl            116.3 MB  ← 慢版索引，仅验证用，可删
```

**建议**：加一个 `scripts/clean_cache.py` 清理过期货。

## 五之二、⭐ 审查后的结论修正总览

**审查改变了项目的一个核心结论**：

| | 审查前 | 审查后 |
|---|---|---|
| **重排的价值** | "dev 有效（+2.67%）但 test 未复现 → 可能不可靠" | ⭐ "**取决于第一段强度**：弱段 +22.94% / 中段 +10.88% / 强段 +4.76%" |
| **实践建议** | "先试重排，但要验证" | ⭐ "**看你的第一段多强再决定**：第一段越弱越值得" |
| **方法论教训** | "小效应量脆弱" | "小效应量脆弱，但要区分'真小'与'被天花板压制'" |

这是本次审查的最大价值：**不是发现了更多小 bug，而是纠正了一个会误导实践的结论。**

## 五之三、⭐⭐ 最优 K 随第一段强度变化（审查补充实验②，已完成）

**动机**：实验①证实了"第一段越弱，重排提升越大"（K=20 固定）。
但 E3 的"K=20 是甜点、更大的 K 更差"这个结论是在**强第一段（D2）**下得到的。
弱第一段下候选质量差，是否需要更大的 K？**必须实测。**

**方法**：复用实验①的打分缓存（top-100 已全部打分），套 6 个 K 档
（5/10/20/30/50/100）× 3 个第一段 = 18 组，**零额外打分成本**。

### 结果

**弱第一段：BM25（基线 0.5707，剩余空间 42.9%）**

| K | nDCG@10 | 提升 | 相对 | 占剩余空间 | Cohen's d |
|---|---|---|---|---|---|
| 5 | 0.6057 | +0.0350 | +6.12% | 8.1% | 0.198 |
| 10 | 0.6645 | +0.0938 | +16.44% | 21.9% | 0.511 |
| 20 | 0.7017 | +0.1309 | +22.94% | 30.5% | 0.558 |
| 30 | 0.7251 | +0.1543 | +27.04% | 36.0% | 0.603 |
| 50 | 0.7475 | +0.1768 | +30.98% | 41.2% | 0.642 |
| **100** | **0.7776** | **+0.2069** | **+36.25%** | **48.2%** | **0.686** |

> ⚠️ **K=100 是网格边界，说明最优点可能还在更大的 K 处**——
> 但打分缓存只到 top-100（第一段检索深度），本审查无法验证 K>100。
> 这是一个**明确的未解点**，不能宣称"K=100 是最优"。

**中第一段：D1（基线 0.7474，剩余空间 25.3%）**

| K | nDCG@10 | 提升 | 相对 | 占剩余空间 | Cohen's d |
|---|---|---|---|---|---|
| 10 | 0.8106 | +0.0631 | +8.45% | 25.0% | 0.382 |

| 30 | 0.8326 | +0.0851 | +11.39% | 33.7% | 0.404 |
| 50 | 0.8354 | +0.0880 | +11.77% | 34.8% | 0.396 |
| **100** | **0.8386** | **+0.0912** | **+12.20%** | **36.1%** | 0.388 |

> 曲线在 K=30 之后已趋于平缓（+11.39% → +12.20%），增量收益很小。

**强第一段：D2（基线 0.8154，剩余空间 18.5%）**

| K | nDCG@10 | 提升 | 相对 | 占剩余空间 | Cohen's d |
|---|---|---|---|---|---|
| 5 | 0.8083 | **-0.0070** | **-0.86%** | -3.8% | -0.042（ns） |
| 10 | 0.8521 | +0.0367 | +4.50% | 19.9% | 0.226 |
| **20** | **0.8542** | **+0.0388** | **+4.76%** | **21.0%** | 0.215 |
| 30 | 0.8530 | +0.0376 | +4.61% | 20.4% | 0.199 |
| 50 | 0.8524 | +0.0370 | +4.54% | 20.0% | 0.188 |
| 100 | 0.8482 | +0.0328 | +4.03% | 17.8% | 0.165 |

> ⭐ 强第一段下 **K=5 反而有害**（-0.86%，不显著），K=20 后开始单调下降。

### ⭐⭐ 核心结论：最优 K 强烈依赖第一段强度

| 第一段 | 基线 | **最优 K（网格内）** | 重排后 | 提升 | Cohen's d |
|---|---|---|---|---|---|
| BM25（弱） | 0.5707 | **100**（边界） | 0.7776 | **+36.25%** | **0.686（中-大）** |
| D1（中） | 0.7474 | **100**（≈30 后平缓） | 0.8386 | +12.20% | 0.388 |
| D2（强） | 0.8154 | **20** | 0.8542 | +4.76% | 0.215 |

```
⭐⭐ 两个决定性发现：

① 弱第一段用大 K（100），强第一段用小 K（20）
   → 「K=20 是甜点」这个原结论【只在强第一段成立】
   → 泛化到所有场景用 K=20，会严重低估重排在弱段的价值
      （K=20 时 +22.94%，K=100 时 +36.25%，差 13 个百分点）

② 强第一段下 K 太小反而有害（K=5 时 -0.86%）
   → 候选太少，重排没有足够的选择空间，反而打乱了原本正确的顺序
```

**机理**：
```
弱第一段（BM25）→ 它的 top-100 里混着大量不相关段落
                → 给重排更多候选，重排能从中挑出被埋没的正确段落
                → K 越大越好（直到第一段深度上限）

强第一段（D2）→ top-100 已经很准，前面的都对
                → 扩大 K 只是把更差的段落纳入重排范围
                → K 要在"够挑"和"少噪声"之间取平衡（20 左右）
```

### ⚠️ 本实验的明确局限

| 局限 | 说明 |
|---|---|
| **K 上界受限** | 打分缓存只到 top-100（第一段检索深度）。弱段的最优点可能是 K>100，**未验证** |
| **单 seed** | 与审查实验①相同的 1,500 query，未做多 seed |
| **仅 dev** | test 已锁定，未在 test 上验证 |
| **单一重排模型** | 只用 bge-reranker-base |
| **延迟未重测** | K=100 的延迟是 K=20 的 5 倍（约 415 ms），弱段的净收益需结合成本权衡 |

**⭐ 实践建议（基于本实验，带条件）**：
```
若你的第一段较弱（nDCG@10 < 0.7）：
    → 用大 K（≥50），本实验 K=100 时 +36.25%，且收益仍在增长
    → 但要权衡延迟（K=100 ≈ 415 ms/query）

若第一段中等（0.7–0.8）：
    → K≈30 已接近饱和（+11.39% vs K=100 的 +12.20%）

若第一段很强（>0.8）：
    → K=20 左右最划算，K 太大反而变差
    → 且不要用 K<10（K=5 时有害）
```

### 核心短板

```
⭐ 本项目最强的能力是「把已经选定的实验做严谨」，
   最弱的环节是「实验设计的覆盖度」。

具体表现：
  · 重排只在强第一段下测（S1）—— 没有分段对照
  · 混合只在质量悬殊时测（M4）—— 没有接近质量的对照
  · 分块只在段落级评测下测（项目已承认）—— 没有块级对照
        ↓
  三个负面结果，每一个都【缺乏关键对照】。
  这不影响「在测试条件下结论成立」，但严重限制了结论的推广范围，
  而项目在表述时【倾向于把条件结论说成普遍结论】。
```

### 一句话结论

> **这是一个"执行严谨、但结论解读有偏差"的项目。**
> 数据和代码的可信度高，负面结果的勇气可嘉；
> 但**核心缺陷是把"天花板效应"误读成了"方法无效"**，这直接影响实践建议。
>
> ⭐ **好消息**：该缺陷已在本次审查中通过补做对照实验修正
> （重排在弱第一段下实测 **+22.94%**，不是"未复现"）。
> 补齐剩余 P0（弱段最优 K）后，项目的可信度将显著提升。
