## 一、主数据集：DuReader-retrieval

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 全称 | DuReader-Retrieval: A Large-scale Chinese Benchmark for Passage Retrieval from Web Search Engine |
| 来源 | 百度 |
| 论文 | ACL EMNLP 2022 |
| 任务 | 中文段落检索（Passage Retrieval） |
| 规模 | 97K queries / 890 万 unique passages |
| 数据类型 | 真实搜索引擎用户日志 |
| 标注 | 自带二元相关性标注（相关 / 不相关） |
| 许可 | 学术研究使用 |

### 1.2 选型理由

- 国内直连：ModelScope 上有镜像，无需翻墙
- 自带相关性标注：不需要自行标注，指标可客观计算，可与论文对比
- 规模适中：可先用子集（10 万段落）跑通，再上全量验证，8GB 显存 / 32GB 内存够用
- 中文原生：语料来自真实中文网页，不是翻译数据集

### 1.3 规模风险

890 万段落约 17.8 亿字。用 BGE-small 编码，CPU 约 50 段落/秒需约 49 小时，GPU（RTX 4060）约 500 段落/秒需约 5 小时，向量存储约 18 GB。因此全量必须用 GPU 加分批处理，并预留磁盘。

### 1.4 分阶段策略

| 阶段 | 语料规模 | 目的 | 可行性 |
|---|---|---|---|
| 阶段 1 | 1 万段落 | 跑通全流程、调试代码 | 秒级 |
| 阶段 2 | 10 万段落 | 出初步对比结果 | 分钟级 |
| 阶段 3 | 100 万段落 | 验证规模效应 | 需 GPU |
| 阶段 4 | 890 万全量 | 复现论文 | 需数小时 + 18GB 磁盘 |

本项目主线做到阶段 2 或 3，全量作为可选项。这一策略本身体现了"先小规模验证，再扩展"的工程思维。

## 三、统一数据格式

### 3.1 语料库格式（JSONL）

```jsonl
{"id": "p_0000001", "text": "南昌大学是江西省唯一一所国家'双一流'建设高校……", "title": "南昌大学简介"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| id | str | 段落唯一标识（用于计算指标） |
| text | str | 段落正文 |
| title | str | 标题（可选） |

### 3.2 查询格式（JSONL）

```jsonl
{"qid": "q_0001", "query": "南昌大学有哪些重点学科？", "relevant_ids": ["p_0000001", "p_0000042"]}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| qid | str | 查询唯一标识 |
| query | str | 查询文本 |
| relevant_ids | list[str] | 相关段落的 id 列表（评测核心） |

relevant_ids 可能为空列表（该 query 无标注相关段落），按评测协议这些 query 应在统计时过滤并记录数量。

## 四、数据预处理规范

### 4.1 必须做的清洗

| # | 操作 | 理由 |
|---|---|---|
| 1 | 去除 HTML 标签 | 原始数据来自网页 |
| 2 | 去除多余空白 | 网页文本常有大量换行/空格 |
| 3 | 处理全角/半角 | 中文标点统一（可选） |
| 4 | 过滤过短段落 | 如 < 20 字，多半是噪声 |
| 5 | 过滤过长段落 | 如 > 1000 字，需截断或分块 |
| 6 | 去重 | 网页内容常重复 |

### 4.2 关于分块

这是 E4 实验的核心变量，但基线阶段要固定策略：

| 策略 | 做法 | 优缺点 |
|---|---|---|
| A. 不切分 | 用数据集原生的 passage | 与论文可比 |
| B. 固定长度 | 如 256 字，重叠 50 字 | 简单可控 |
| C. 按段落 | 按 `\n\n` 切 | 语义完整 |
| D. 语义分块 | 用嵌入相似度找边界 | 复杂，效果未必好 |

基线阶段用 A（不切分），因为要与论文对比，必须用原始 passage 定义，E4 才系统对比不同策略。

## 五、数据集统计

下载后必须统计数据并记录：

- 语料库段落数、查询数
- 平均/中位数/最大相关段落数
- 有多少 query 的相关段落数为 0（要被过滤）
- 段落长度分布（均值、中位数、P95）
- 训练/验证/测试划分的实际数量

这些数字必须写进实验报告，因为指标值与数据分布强相关，不比数据分布就比指标是无效对比。实际统计见 data/DATACARD.md。

## 六、数据集划分

### 6.1 划分原则

测试集只用一次：train（官方）切出 dev 用于调参，test（官方）只在最终报告时跑一次。

| 集合 | 来源 | 用途 |
|---|---|---|
| train | 官方 86,395 条 | 训练/微调（本项目主要是调参） |
| dev | 从 train 切分 | 调超参数 |
| test | 官方 2,000 条 | 只跑一次，用于报告 |

### 6.2 语料库的特殊性

检索任务的语料库不划分：训练集和测试集共用同一个语料库，因为检索的任务就是"从全库里找"。划分只针对 query。

## 七、已知问题与注意事项

| # | 问题 | 应对 |
|---|---|---|
| 1 | 数据集可能有脏标注 | 检查 relevant_ids 是否指向真实存在的段落 id |
| 2 | 部分 query 无相关段落 | 过滤 + 记录 |
| 3 | ModelScope 版是采样的 | 在报告中说明，不与全量论文指标直接比 |
| 4 | 数据许可 | 仅用于学术研究，不得商用，引用原论文 |
| 5 | 下载可能失败 | 准备备选（C-MTEB 版本），脚本自动重试 |

使用本数据集必须引用原论文：Qiu et al., DuReader-Retrieval: A Large-scale Chinese Benchmark for Passage Retrieval from Web Search Engine, EMNLP 2022。

## 九、检查清单

- 语料库下载完整（段落数不少于计划数）

- 数据集统计已产出并记录
- 检查过 relevant_ids 的有效性
- 记录了过滤掉的 query 数量
- dev 集已切分并固定（保存为文件，不再重新切）
- 测试集已锁定，未用于任何调参
- 数据集引用信息已记录到报告
