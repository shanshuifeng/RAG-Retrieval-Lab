## 一、核心原则

一次只改一个变量：E1 只改检索方法，其余全部不变。若同时换嵌入模型、融合方法、K 值，就无法归因提升来自哪里。

每个实验必须固定的公共配置：

| 配置项 | 固定值 | 说明 |
|---|---|---|
| 语料库规模 | 见各实验 | 同一实验内必须一致 |
| 查询集 | dev（调参）/ test（报告） | 不混用 |
| K 值 | 报告 1/5/10/20/100 | 统一口径 |
| 随机种子 | 固定（如 42） | 保证可复现 |

## 二、E1 · 基线对比（BM25 vs 稠密检索）

### 2.1 研究问题

Q1：在中文检索任务上，稠密向量检索比 BM25 好多少？

### 2.2 为什么先做基线

必须先建基线：验证评测脚本是否正确（若 BM25 跑不出合理数字，说明评测代码有 bug 而非模型不好）；后续所有提升都相对基线而言；文献中 BM25 通常有公开数字可对照。

### 2.3 实验组

| 组 | 方法 | 配置 |
|---|---|---|
| B0 | BM25 | k1=1.5, b=0.75 |
| B1 | BM25 调参 | 网格搜索 k1∈{0.9,1.2,1.5,2.0}, b∈{0.3,0.5,0.75,0.9} |
| D1 | 稠密检索（BGE-small） | BAAI/bge-small-zh-v1.5 |
| D2 | 稠密检索（BGE-base） | BAAI/bge-base-zh-v1.5 |
| D3 | 稠密检索（其他） | shibing624/text2vec-base-chinese |

### 2.4 BM25 原理

$$\text{score}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1+1)}{f(t,d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$

| 符号 | 含义 | 作用 |
|---|---|---|
| f(t,d) | 词 t 在文档 d 中的频次 | 词出现越多越相关 |
| IDF(t) | 逆文档频率 | 稀有词权重高 |
| k1 | 词频饱和参数 | 控制词频收益递减 |
| b | 长度归一化参数 | 控制长文档惩罚 |

中文 BM25 必须解决分词问题：BM25 基于"词"，而中文没有空格，必须分词（jieba / HanLP / pkuseg）。分词质量直接影响 BM25 效果。

### 2.5 稠密检索原理

离线阶段把全部 passage 编码成向量并建 FAISS 索引；在线阶段把 query 编码成向量，在向量空间找最近的 K 个，相似度用余弦相似度（或归一化后的内积）。这正是 Course 3 双塔架构在 RAG 里的应用：query 塔与 passage 塔各自编码后算点积。

### 2.6 预期结果

| 预期 | 依据 |
|---|---|
| 稠密检索在语义匹配上优于 BM25 | 处理同义词、改写 |
| BM25 在精确关键词匹配上仍有优势 | 专有名词、代码 |
| 两者可能互补 | 这是 E2 的动机 |

若结果与预期不符，先排查分词、嵌入模型、语料规模、评测脚本，排查无误仍如此则如实报告。

## 三、E2 · 混合检索

### 3.1 研究问题

Q2：把稀疏和稠密检索融合，能比单一方法更好吗？

### 3.2 动机

两种方法的失效模式不同：BM25 擅长精确匹配（专有名词、编号），弱于语义改写；稠密擅长语义相似，弱于精确匹配（罕见实体易被平滑掉）。失效模式不同意味着融合可能互补。

### 3.3 融合方法 RRF（Reciprocal Rank Fusion）

$$\text{RRF}(d) = \sum_{r \in R}\frac{1}{k + \text{rank}_r(d)}$$

| 符号 | 含义 | 典型值 |
|---|---|---|
| R | 参与融合的检索器集合 | {BM25, 稠密} |
| rank_r(d) | 文档 d 在检索器 r 中的排名 | 1, 2, 3, … |
| k | 平滑常数 | 通常 60 |

用倒数排名而非分数的原因：BM25 的分数范围（如 0–30）与余弦相似度（0–1）不可比，直接相加没有意义，而归一化本身会引入新不确定性。RRF 只用排名（跨检索器可比的 1,2,3...），规避了量纲问题。

### 3.4 实验组

| 组 | 方法 | 说明 |
|---|---|---|
| 基线 | E1 中最优的单方法 | 用于对比 |
| H1 | RRF 融合（k=60） | 标准做法 |
| H2 | RRF 调参 | k∈{10,30,60,100} |
| H3 | 加权分数融合 | 归一化后加权，α∈{0.3,0.5,0.7} |
| H4 | 各取 Top-N 后合并 | 简单策略，作对照 |

召回数量的约定：两个检索器取的数量要一致（公平），融合后的 K 与单方法的 K 要能对比。

### 3.5 预期结果

| 情形 | 解读 |
|---|---|
| 混合 > 单方法 | 互补性成立 |
| 混合 ≈ 最好单方法 | 另一路没贡献 |
| 混合 < 最好单方法 | 融合策略有问题 |

负面结果同样有价值：若混合没提升，如实写"在这个数据/规模下，混合的收益不足以抵消额外成本"。

## 四、E3 · 重排序

### 4.1 研究问题

Q3：加一个 Cross-encoder 重排序器，值不值？

### 4.2 Bi-encoder vs Cross-encoder

Bi-encoder（双编码器）用于召回：query 与 passage 分别编码后算点积。优点是 passage 向量可离线预计算，检索极快；缺点是 query 与 passage 没有交互，精度受限。

Cross-encoder（交叉编码器）用于重排：query 与 passage 拼接送入同一模型。优点是能捕捉细粒度交互，精度高；缺点是无法预计算，每个 (query, passage) 对都要跑一次，只能用于少量候选。

### 4.3 为什么必须两阶段

若只用 Cross-encoder 检索，890 万段落每个 query 都要跑一次模型，完全不可行。因此必须两阶段：先用 Bi-encoder / BM25 把全库筛出候选 100 个（快，向量可预计算），再用 Cross-encoder 精排（慢但只跑 100 次）。用"快而不准"筛出候选，用"慢而准"精排。

### 4.4 实验组

| 组 | 配置 | 说明 |
|---|---|---|
| 基线 | E2 最优（无重排序） | 对比基准 |
| R1 | + BGE-reranker-base | 主流中文重排序模型 |
| R2 | + BGE-reranker-large | 更大模型，看收益是否值得 |
| R3 | 只重排 Top-20 | 看重排多少候选的影响 |
| R4 | 只重排 Top-50 | 同上 |
| R5 | 只重排 Top-100 | 同上 |

重排候选数的影响是一个有价值的分析：重排越多，效果上限越高但越慢，收益递减点在哪里，直接回答"我该重排多少"这个工程问题。

### 4.5 成本对比

| 方法 | 延迟 | 显存 | nDCG@10 |
|---|---|---|---|
| BM25 | 约 10ms | 0 | ? |
| 稠密 | 约 50ms | 约 1GB | ? |
| 混合 | 约 60ms | 约 1GB | ? |
| + 重排序 | 约 500ms+ | 约 2GB | ? |

必须报告成本，因为"提升 2% 但慢 10 倍"是一个重要的工程结论。

## 五、E4 · 分块策略消融

### 5.1 研究问题

Q4：文档怎么切，对检索效果影响多大？

### 5.2 为什么有价值

分块是 RAG 里最容易被忽视但影响极大的环节。切太碎则语义不完整，切太大则噪声多，重叠多少影响边界信息，这个问题很少有公开的定量答案。

### 5.3 实验组

| 组 | 策略 | 配置 |
|---|---|---|
| C0 | 不切分（原生 passage） | 对照组（与论文可比） |
| C1 | 固定长度 128 字 | overlap=0 |
| C2 | 固定长度 256 字 | overlap=0 |
| C3 | 固定长度 512 字 | overlap=0 |
| C4 | 256 字 + 重叠 50 | 看重叠的作用 |
| C5 | 按段落切分 | 按 \n\n |
| C6 | 按句子聚合 | 累积到阈值再切 |

### 5.4 本实验的特殊难点

切分后原有的 (query, passage_id) 标注失效，需判定哪个 chunk 相关。常用简化规则：若原 passage 相关，则它的所有 chunk 都算相关（宽松），或只把包含答案的 chunk 算相关（严格，需额外标注）。本项目采用宽松规则，并在报告中说明。

### 5.5 预期结果

| 策略 | 预期 |
|---|---|
| C0（原生） | 通常最好，因数据集按 passage 设计 |
| C1（128字） | 可能过碎，语义不完整 |
| C2（256字） | 常见平衡点 |
| C4（有重叠） | 比 C2 略好，代价是索引变大 |

## 七、执行纪律

1. 一次只改一个变量
2. 测试集只用一次，调参一律在 dev
3. 记录失败配置，失败比成功更有信息量
4. 报成本，不只报效果
5. 提升必须做显著性检验
