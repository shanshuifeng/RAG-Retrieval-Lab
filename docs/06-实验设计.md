## 零、⭐ 实验设计的核心原则

```
⭐⭐ 一次只改一个变量（Control Variables）

   ✅ 正确：E1 只改【检索方法】，其他全不变
   ❌ 错误：E2 同时换了嵌入模型 + 融合方法 + K 值
            → 提升到底来自哪个？无法归因
        ↓
   ⭐ 这是整个实验设计的铁律
```

**每个实验必须固定的"公共配置"：**

| 配置项 | 固定值 | 说明 |
|---|---|---|
| 语料库规模 | 见各实验 | ⚠️ **同一实验内必须一致** |
| 查询集 | dev（调参）/ test（报告） | 不混用 |
| K 值 | 报告 1/5/10/20/100 | 统一口径 |
| 随机种子 | 固定（如 42） | 保证可复现 |

## 一、E1 · 基线对比（BM25 vs 稠密检索）

### 1.1 研究问题

> **Q1：在中文检索任务上，稠密向量检索比 BM25 好多少？**

### 1.2 为什么这是第一个实验

```
⭐ 必须先建基线，原因有三：

① 验证评测脚本是否正确
     如果 BM25 在你手上跑不出"合理"的数字，
     说明【评测代码有 bug】，而不是模型不好
        ↓
② ⭐ 后续所有提升都相对基线而言
     没有基线，"提升了 5%" 毫无意义
        ↓
③ 文献里 BM25 通常有公开数字可对照
        ↓
   ⭐ 对得上 → 说明流程正确 → 可以继续
```

### 1.3 实验组

| 组 | 方法 | 配置 |
|---|---|---|
| **B0** | ⭐ **BM25** | $k_1 = 1.5$, $b = 0.75$ |
| **B1** | BM25 调参 | 网格搜索 $k_1 \in \{0.9, 1.2, 1.5, 2.0\}$, $b \in \{0.3, 0.5, 0.75, 0.9\}$ |
| **D1** | 稠密检索（BGE-small） | `BAAI/bge-small-zh-v1.5` |
| **D2** | 稠密检索（BGE-base） | `BAAI/bge-base-zh-v1.5` |
| **D3** | 稠密检索（其他） | `shibing624/text2vec-base-chinese` |

### 1.4 BM25 原理回顾

$$\Large \text{score}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1+1)}{f(t,d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$

| 符号 | 含义 | 作用 |
|---|---|---|
| $f(t,d)$ | 词 $t$ 在文档 $d$ 中的频次 | 词出现越多越相关 |
| $\text{IDF}(t)$ | 逆文档频率 | ⭐ **稀有词权重高** |
| $k_1$ | 词频饱和参数 | ⭐ 控制"词频收益递减" |
| $b$ | 长度归一化参数 | ⭐ 控制"长文档惩罚" |

**⭐ 中文 BM25 必须解决分词问题：**

```
⚠️ BM25 基于"词"，但中文没有空格
        ↓
   必须分词：jieba / HanLP / pkuseg
        ↓
⭐ 分词质量直接影响 BM25 效果
   → 这是中文检索相对于英文的额外难点
```

### 1.5 稠密检索原理回顾

```
⭐ 流程（呼应 Course 3 第 122/123 P）：

  Step 1  离线：把全部 passage 编码成向量，建 FAISS 索引
             passage → [编码器] → 向量 (512维) → 存入 FAISS

  Step 2  在线：把 query 编码成向量
             query → [编码器] → 向量 (512维)

  Step 3  检索：在向量空间里找最近的 K 个
             ⭐ 相似度 = 余弦相似度（或归一化后的内积）
                ← 这正是 Course 3 第 122 P 学的"点积"
```

> 🔗 **Course 3 第 122 P 学的双塔（Two-Tower）架构，在 RAG 里就是"双编码器（Bi-Encoder）"**：
> **query 塔 + passage 塔，各自编码后算点积。**

### 1.6 预期结果与解读

| 预期 | 依据 |
|---|---|
| 稠密检索在**语义匹配**上优于 BM25 | 处理同义词、改写 |
| BM25 在**精确关键词**匹配上仍有优势 | 如专有名词、代码 |
| ⭐ **两者可能互补** | → 这正是 E2 的动机 |

**⚠️ 如果结果与预期不符（如 BM25 更好）：**

```
⭐ 不要慌，先排查：

□ 分词是否正确？（中文分词错误会严重损害 BM25）
□ 嵌入模型是否适合中文？（用错模型很常见）
□ 语料库规模是否太小？（太小则稠密检索优势体现不出来）
□ 评测脚本是否正确？（用 BM25 的结果对照文献）

⭐ 如果排查无误仍然如此 → 【如实报告】
   这本身就是一个有价值的发现（"在这个数据规模下……"）
```

### 1.7 产出

```
results/E1_baseline.json
  · 各组在 Recall@{1,5,10,20,100}、MRR@10、nDCG@10 上的分数
  · ⭐ BM25 最优超参数
  · 推理耗时 / 内存占用（成本对比）
```

## 二、E2 · 混合检索（Hybrid Retrieval）

### 2.1 研究问题

> **Q2：把稀疏和稠密检索融合，能比单一方法更好吗？**

### 2.2 动机

```
⭐ 两种方法的失效模式【不同】：

  BM25 擅长：精确匹配（专有名词、编号、引用）
  BM25 弱点：语义改写（"怎么退货" vs "退款流程"）

  稠密 擅长：语义相似
  稠密 弱点：精确匹配（罕见实体容易被"平滑"掉）
        ↓
  ⭐ 既然失效模式不同 → 融合可能互补 ✅
```

### 2.3 ⭐ 融合方法：RRF（Reciprocal Rank Fusion）

**这是工业界最常用的融合方法**（因为它**不需要归一化分数**）：

$$\Large \text{RRF}(d) = \sum_{r \in R}\frac{1}{k + \text{rank}_r(d)}$$

| 符号 | 含义 | 典型值 |
|---|---|---|
| $R$ | 参与融合的检索器集合 | {BM25, 稠密} |
| $\text{rank}_r(d)$ | 文档 $d$ 在检索器 $r$ 中的排名 | 1, 2, 3, … |
| $k$ | 平滑常数 | ⭐ **通常 60** |

**⭐ 为什么用倒数排名而不是分数？**

```
⚠️ 问题：BM25 的分数范围（如 0–30）与余弦相似度（0–1）【不可比】
        ↓
   直接相加没有意义 → 需要归一化
        ↓
⚠️ 但归一化本身也是个问题：
   · 分数分布随 query 变化
   · 归一化方法的选择会引入新的不确定性
        ↓
⭐ RRF 的巧妙之处：
   只用【排名】，不用分数
        ↓
   排名是跨检索器可比的（都是 1,2,3...）✅
```

### 2.4 实验组

| 组 | 方法 | 说明 |
|---|---|---|
| **基线** | E1 中最优的单方法 | 用于对比 |
| **H1** | RRF 融合（k=60） | ⭐ 标准做法 |
| **H2** | RRF 调参 | $k \in \{10, 30, 60, 100\}$ |
| **H3** | 加权分数融合 | 归一化后加权，$\alpha \in \{0.3, 0.5, 0.7\}$ |
| **H4** | 各取 Top-N 后合并 | 简单策略，作对照 |

### 2.5 ⚠️ 关键设计细节

```
⭐ 召回数量怎么定？

  若 BM25 取 Top-100、稠密取 Top-100
      → 融合后候选池最多 200 个（实际去重后更少）
        ↓
  ⭐ 然后从融合结果里取 Top-K 计算指标

⚠️ 注意：
   · 两个检索器【取的数量要一致】（公平）
   · 融合后的 K 与单方法的 K 要能对比
```

### 2.6 预期结果

| 情形 | 解读 |
|---|---|
| ✅ 混合 > 单方法 | 说明互补性成立，值得上 |
| ⚠️ 混合 ≈ 最好单方法 | 说明另一路没贡献，**可考虑砍掉** |
| ❌ 混合 < 最好单方法 | ⚠️ 融合策略有问题（如 RRF 的 k 不合适） |

> ⭐ **负面结果也有价值**：如果混合没提升，就**如实写"在这个数据/规模下，混合检索的收益不足以抵消额外的计算成本"**。

## 三、E3 · 重排序（Reranking）⭐

### 3.1 研究问题

> **Q3：加一个 Cross-encoder 重排序器，值不值？**

### 3.2 ⭐⭐ Bi-encoder vs Cross-encoder（核心概念）

**这是本实验最重要的理论点：**

```
【Bi-encoder（双编码器）】← 召回阶段用

    query  ──► [编码器A] ──► 向量_q ─┐
                                    ├──► 点积 ──► 相似度
    passage ─► [编码器B] ──► 向量_p ─┘
                                    ↑
                        ⭐ query 和 passage 【分别】编码

    ✅ 优点：passage 向量【可离线预计算】→ 检索极快
             （这正是 Course 3 第 123 P 的"离线预计算"）
    ❌ 缺点：query 和 passage 【没有交互】→ 精度受限


【Cross-encoder（交叉编码器）】← 重排序阶段用

    [query, passage] ──► [编码器] ──► 相关性分数
          ↑
    ⭐ query 和 passage 【拼在一起】送入模型

    ✅ 优点：能捕捉细粒度交互 → 精度高
    ❌ 缺点：⚠️ 【无法预计算】
            每个 (query, passage) 对都要跑一次
            → 只能用于【少量候选】的重排序
```

### 3.3 ⭐⭐ 为什么必须"两阶段"？

```
⚠️ 如果只用 Cross-encoder 检索：

    890 万段落 × 每个 query 都要跑一次模型
        = 890 万次前向传播 / query ⚠️
        → 完全不可行

⭐ 所以必须两阶段：

    ① 召回（Bi-encoder / BM25）：全库 890 万 → 候选 100 个
        ⭐ 快，因为向量可预计算
              ↓
    ② 重排序（Cross-encoder）：100 个候选 → 精排
        ⭐ 慢但只跑 100 次，可接受
              ↓
    ⭐ 用"快而不准"筛出候选，用"慢而准"精排
```

> 🔗 **这完全是 Course 3 第 123 P 讲的"召回 + 排序"架构**：
> **"召回步骤的目标是确保广泛的覆盖……排序步骤对用户实际可能喜欢的物品做更仔细的预测。"**

### 3.4 实验组

| 组 | 配置 | 说明 |
|---|---|---|
| **基线** | E2 最优（无重排序） | 对比基准 |
| **R1** | + BGE-reranker-base | 主流中文重排序模型 |
| **R2** | + BGE-reranker-large | 更大模型（看收益是否值得） |
| **R3** | 只重排 Top-20 | ⭐ 看"重排多少候选"的影响 |
| **R4** | 只重排 Top-50 | 同上 |
| **R5** | 只重排 Top-100 | 同上 |

### 3.5 ⭐ 关键实验：重排候选数的影响

```
⭐ 这是一个很有价值的分析：

    重排 Top-20  vs  Top-50  vs  Top-100
        ↓
    · 重排越多 → 效果上限越高，但越慢
    · ⭐ 收益递减点在哪里？
        ↓
    这直接回答了工程问题："我该重排多少？"
```

**预期曲线：**

```
nDCG@10
  ↑
  │        ╭────────────  ← 收益递减
  │      ╱
  │    ╱
  │  ╱
  └──────────────────────► 重排候选数
    20   50   100   200

⭐ 典型结论：重排 Top-50 是性价比拐点
   （超过之后提升 < 1%，但耗时翻倍）
```

### 3.6 成本对比（必须报告）

| 方法 | 延迟 | 显存 | nDCG@10 |
|---|---|---|---|
| BM25 | ~10ms | 0 | ? |
| 稠密 | ~50ms | ~1GB | ? |
| 混合 | ~60ms | ~1GB | ? |
| **+ 重排序** | ⚠️ **~500ms+** | ~2GB | ? |

> ⭐ **必须报告成本**——因为**"提升 2% 但慢 10 倍"是一个重要的工程结论**，不是次要信息。

## 四、E4 · 分块策略消融（Chunking Ablation）

### 4.1 研究问题

> **Q4：文档怎么切，对检索效果影响多大？**

### 4.2 为什么这个实验有价值

```
⭐ 分块是 RAG 里【最容易被忽视、但影响极大】的环节

    很多教程默认"随便切 500 字"
        ↓
    但实际上：
      · 切太碎 → 语义不完整（"它"指代不明）
      · 切太大 → 噪声多（关键信息被淹没）
      · 重叠多少 → 影响边界信息
        ↓
    ⭐ 这个问题很少有公开的定量答案
```

### 4.3 实验组

| 组 | 策略 | 配置 |
|---|---|---|
| **C0** | ⭐ **不切分**（原生 passage） | 对照组（与论文可比） |
| **C1** | 固定长度 128 字 | overlap=0 |
| **C2** | 固定长度 256 字 | overlap=0 |
| **C3** | 固定长度 512 字 | overlap=0 |
| **C4** | 256 字 + 重叠 50 | 看重叠的作用 |
| **C5** | 按段落切分 | 按 `\n\n` |
| **C6** | 按句子聚合 | 累积到阈值再切 |

### 4.4 ⚠️ 本实验的特殊难点

```
⚠️ 切分后，原有的 (query, passage_id) 标注【失效了】

    原来：query_1 相关于 passage_42
    切分后：passage_42 变成了 passage_42_chunk_0/1/2
        ↓
    怎么判定哪个 chunk 相关？
        ↓
⭐ 常用的简化规则：
    若原 passage 相关，则它的【所有 chunk】都算相关
        （宽松）
    或：只把【包含答案的 chunk】算相关
        （严格，但需要额外标注）
        ↓
⭐ 本项目采用【宽松规则】，并在报告中明确说明
```

### 4.5 预期结果

| 策略 | 预期 |
|---|---|
| **C0（原生）** | 通常最好——因为数据集就是按 passage 设计的 |
| **C1（128字）** | ⚠️ 可能过碎，语义不完整 |
| **C2（256字）** | 常见平衡点 |
| **C4（有重叠）** | 比 C2 略好，代价是索引变大 |

> ⭐ **这个实验的现实意义**：
> **当你要处理自己的文档时，该切多大？** —— 本实验给出数据支撑的答案。

## 六、⚠️ 实验执行纪律

```
⭐ 五条铁律：

① 【一次只改一个变量】
   否则无法归因

② 【测试集只用一次】
   调参一律在 dev 上

③ 【记录失败配置】
   失败比成功更有信息量

④ 【报成本，不只报效果】
   "提升 2% 但慢 10 倍"是重要结论

⑤ 【提升必须做显著性检验】
   提升 < 1% 时尤其需要
```
