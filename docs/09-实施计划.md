# 09 · 实施计划

> 文档版本：v1.0 ｜ 创建日期：2026-10-16
> 总工期：约 3–4 周（业余时间）

---

## 一、总览

M0 环境搭建 → M1 数据准备 → M2 E1 基线 → M3 E2 混合 → M4 E3 重排序 → M5 E4 分块 → M6 报告。M4 之后是核心价值点。

---

## 二、分阶段任务分解

### M0 · 环境搭建（1 天）

- M0.1 建目录结构
- M0.2 写文档
- M0.3 装 CPU 最小依赖（PyYAML、tqdm、requests、jieba、rank_bm25）
- M0.4 写 check_env.py
- M0.5 写 requirements.txt
- M0.6 建 git 仓库 + .gitignore

M0.3 只装 CPU 依赖，先跑通流程降低风险。

### M1 · 数据准备（2–3 天）

- M1.1 探测数据源可达性
- M1.2 下载数据集
- M1.3 格式转换
- M1.4 数据统计（DATACARD + stats.json）
- M1.5 切分 dev 集，固定保存
- M1.6 小规模验证（1 万段落子集）

风险点：数据集可能很大（890 万段落），先用 1 万段落跑通，全量留到最后。

### M2 · E1 基线实验（3–5 天）

- M2.1 实现 BM25 检索器
- M2.2 实现评测指标
- M2.3 验证指标正确性（单元测试，理想排序 → nDCG=1.0）
- M2.4 跑 BM25 基线，与文献对照
- M2.5 装向量依赖
- M2.6 实现稠密检索
- M2.7 跑稠密检索对比

M2.3 是最关键的一步：指标代码错了则后面所有结论都是错的，因此必须写单元测试、与文献基线对照，对不上就查缺陷。

### M3 · E2 混合检索（3–5 天）

实现 RRF 融合，跑混合检索对比，RRF 参数调优，对比加权融合。无论提升与否都如实记录。

### M4 · E3 重排序（3–5 天）

实现 Cross-encoder，跑重排序实验，重排候选数消融，成本对比，显著性检验。M4 是本项目最有价值的实验，回答"加个重排序值不值"这个最实际的工程问题。

### M5 · E4 分块消融（2–3 天）

实现多种分块策略，跑分块对比，分析分块影响。分块会破坏原标注，需明确说明处理规则。

### M6 · 报告撰写（2–3 天）

汇总结果、生成图表、撰写报告、写局限说明、更新 README。

## 六、常见拖延陷阱

| 陷阱 | 表现 | 破解 |
|---|---|---|
| 追求完美环境 | 花一周调 CUDA | 先 CPU 跑通 |
| 追求大数据 | 一上来就全量 890 万 | 1 万 → 10 万 → 100 万 |
| 指标没验证就往下做 | 结果奇怪但不查 | M2.3 是硬门槛 |
| 同时改多个变量 | 无法归因 | 一次一个变量 |
| 只跑不记录 | 两周后忘了怎么跑 | 每次实验必记录 |
| 想一次写完报告 | 最后几天手忙脚乱 | 每个里程碑写小结 |

## 八、项目复盘（2026-10-24 完成，2026-10-31 补充）

### 计划 vs 实际

| 项 | 计划 | 实际 |
|---|---|---|
| 工期 | 3–4 周 | 约 8 天 |
| 里程碑 | M0–M6 | 全部完成（含计划外的 P1 提速、P7 公平成本、三轮复核） |
| 实验 | E1–E4 | 全部完成 + test 最终评测 |

偏差原因：GPU 可用（稠密编码 10 万段 62 秒，而非估算的 1–2 小时）；BM25 提速 173×（16 组网格调参从 5.6 小时降到 95 秒）；分层缓存策略；文档撰写与后台实验并行。

### 最有价值的发现

| # | 发现 | 价值 |
|---|---|---|
| 1 | 换检索范式（d=1.035）远大于一切排序优化（d≈0.12） | 指导工程资源分配：先换方法再调参 |
| 2 | 三个负面结果（混合负优化、分块负优化、重排天花板） | 比"成功"更有信息量，且均有消融证据 |
| 3 | 小效应量结论跨集不稳（dev p=4e-28 → test p=0.625） | 给出准则：d<0.2 时即使 p 极小也要谨慎 |
| 4 | 混合的最优权重是"不混合" | 权重扫描给出决定性证据 |
| 5 | 分块变差来自检索信号受损，非评测口径 | 深度扫描（K 10→100）排除了"位置稀释为主因" |

### 最大的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | mrr_at_k 写成生成器（不报错，指标悄悄偏低） | 不报错的错误最危险，需输入类型多样性测试 |
| 2 | BGE query 指令前缀反而降效果（-1.3%~-2.6%） | 官方推荐不等于你的数据上最优，必须消融 |
| 3 | 索引缓存不含配置（改默认值后仍命中旧缓存） | 缓存键必须含所有影响结果的配置 |
| 4 | hf-mirror 长连接渐进限速 | 短连接小分块，网络问题要实测 |
| 5 | HF xet 后端 401 | 设 HF_HUB_DISABLE_XET=1 |
| 6 | test 首次运行网络超时崩溃 | 强制离线模式，锁机制保障没白费 test |
| 7 | 复核脚本本身有 bug（截断候选集） | 验证工具也要被验证 |
| 8 | .gitignore 行内注释（git 不支持） | 配置规则用 git check-ignore 验证 |

### 如果重做

一开始就上 GPU；一开始就写文档数字与结果 JSON 交叉比对脚本；一开始就给缓存加配置键；单元测试就加输入类型多样性；更早做 dev/test 对照；分块实验更早考虑评测口径问题。

### 下一步可以做什么

| 优先级 | 方向 | 理由 |
|---|---|---|
| P0 | 更大语料（100 万/全量）验证稠密优势 | 本结论可能低估稠密的规模优势 |
| P1 | learned sparse（SPLADE）与多向量（ColBERT）对比 | 填补稀疏与稠密之间的空白 |
| P2 | 换块级标注数据集重做分块实验 | 验证评测口径对结论的影响 |
| P3 | 端到端 RAG 评测 | 本项目只测了检索质量 |
| P4 | 重排模型对比 | 当前只用了一个模型 |
| P5 | 垂直领域数据验证 | 通用网页搜索结论不能外推 |

复盘是学习闭环的最后一环，不做复盘同样的坑还会踩。
