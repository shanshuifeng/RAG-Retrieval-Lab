## 八、⭐ 项目复盘（已完成，2026-10-24）

### 计划 vs 实际

| 项 | 计划 | 实际 |
|---|---|---|
| 工期 | 3–4 周 | **约 8 天** |
| 里程碑 | M0–M6 | M0–M6 **全部完成**（含 plan 外的 P1 提速、P7 公平成本、三轮复核） |
| 实验 | E1–E4 | E1–E4 **全部完成** + test 最终评测 |

**偏差原因**：
```
① GPU 可用（CUDA 13.0 + RTX 4060）：稠密编码 10 万段仅 62 秒，而非估算的 1–2 小时
② BM25 提速 173×（0.85 ms/q）：16 组网格调参从 5.6 小时降到 95 秒
③ 分层缓存策略：索引/分数/结果均可复用，避免重复计算
④ 并行执行：文档撰写与后台实验同时进行
```

### 最有价值的发现

| # | 发现 | 为什么有价值 |
|---|---|---|
| **1** | ⭐ **换检索范式（d=1.035）≫ 一切排序优化（d≈0.12）** | 直接指导工程资源分配：先换方法，再调参 |
| **2** | ⭐ **三个负面结果**（混合负优化、分块负优化、重排未复现） | 比"成功"更有信息量；且全部有消融证据支撑 |
| **3** | ⭐ **小效应量的结论跨集不稳**（dev p=4e-28 → test p=0.625） | 给出实用准则：d<0.2 时即使 p 极小也要谨慎 |
| **4** | 混合的最优权重是"不混合" | 权重扫描给出了决定性证据，不是靠猜 |
| **5** | 分块在段落级评测下有结构性劣势 | 揭示了"分块无用"的真正原因是评测口径，而非方法本身 |

### 最大的坑

| # | 坑 | 教训 |
|---|---|---|
| **1** | `mrr_at_k` 写成生成器（不报错，指标悄悄偏低） | **不报错的错误最危险**；需输入类型多样性测试 |
| **2** | BGE query 指令前缀反而降效果（-1.3%~-2.6%） | 官方推荐 ≠ 你的数据上最优；必须消融验证 |
| **3** | 索引缓存不含配置（改默认值后仍命中旧缓存） | 缓存键必须含所有影响结果的配置 |
| **4** | hf-mirror 长连接渐进限速（325KB/s → 4.6MB/s） | 短连接小分块；网络问题要实测不要猜 |
| **5** | HF xet 后端 401 | `HF_HUB_DISABLE_XET=1` |
| **6** | test 首次运行网络超时崩溃 | 强制离线模式；锁机制保障了没白费 test |
| **7** | 复核脚本本身有 bug（截断候选集） | **验证工具也要被验证** |
| **8** | `.gitignore` 行内注释（git 不支持） | 配置规则要用 `git check-ignore` 验证 |

### 如果重做，会怎么改

```
① 一开始就上 GPU：我按 CPU 估算编码时间，误差 70 倍
② 一开始就写"文档数字 ↔ 结果 JSON"交叉比对脚本：
   手抄数字错误发现太晚（第二轮复核才发现）
③ 一开始就给缓存加配置键：省掉一次"改了没生效"的困惑
④ 单元测试就加"输入类型多样性"：这类 bug 一次测试就能抓住
⑤ 更早做 dev/test 对照：如果能更早发现重排不复现，
   就不会在 dev 阶段花太多精力优化重排的 K
⑥ 分块实验应更早考虑"评测口径"问题：
   段落级投影的稀释效应我是在结果出来后才想清楚的
```

### 下一步可以做什么

| 优先级 | 方向 | 理由 |
|---|---|---|
| **P0** | 在**更大语料**（100 万 / 全量 890 万）上验证稠密优势 | 本结论可能低估了稠密的规模优势 |
| **P1** | 补 **learned sparse**（SPLADE）与**多向量**（ColBERT）对比 | 填补"稀疏 vs 稠密"二元对立之间的空白 |
| **P2** | 换**块级标注**的数据集重做分块实验 | 预期结论会反转，能验证"评测口径决定结论"的假设 |
| **P3** | 端到端 RAG 评测（检索 → 生成） | 本项目只测了检索质量 |
| **P4** | 重排模型对比（bge-reranker-large / Cohere Rerank） | 当前只用了一个模型 |
| **P5** | 在垂直领域数据上验证 | 通用网页搜索的结论不能外推 |
