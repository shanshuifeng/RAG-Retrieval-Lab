# RAG-Retrieval-Lab · 最终实验报告

> **报告性质**：⭐ **项目主报告**（汇总 E1–E4 全部实验）
> **完成日期**：2026-10-24
> **数据集**：DuReader-retrieval（dev 8,640 query / test 2,000 query，各 10 万段落）
> **核心问题**：**RAG 的检索环节，每一层值多少钱？**

---

## 摘要

本项目在一个统一的数据划分与评测协议下，量化比较了中文段落检索的四个关键决策：
**检索范式（稀疏 vs 稠密）、结果融合（混合检索）、排序优化（重排序）、文本切分（分块）**。

**四个核心发现**：

| # | 结论 | 效应量 | 是否在 test 复现 |
|---|---|---|---|
| 1 | 稠密检索远优于 BM25（nDCG@10 **+55.1%**） | d=1.035（大） | ✅ **复现且更强** |
| 2 | 混合检索（RRF）是**负优化**（-12.8%） | d=-0.479 | ✅ **复现** |
| 3 | 重排在 dev 有效（+2.67%）但 **test 上不显著**（+0.16%） | d=0.011 | ❌ **未复现** |
| 4 | 分块全面**劣于**不切分（-0.33% ~ -2.58%） | — | ⚠️ 仅 dev（test 已锁） |

> ⭐ **一句话总结**：**先选对检索范式，其余优化都是边际。**
> 换用稠密检索的效应量（d=1.035）是调参（0.114）的 **9 倍**、重排（0.119）的 **8.7 倍**。

## 一、研究问题与方法

### 1.1 四个问题

| 实验 | 问题 | 主指标 |
|---|---|---|
| **E1** | 稠密向量检索比 BM25 好多少？ | nDCG@10、Recall@10 |
| **E2** | 混合检索（RRF）有提升吗？ | nDCG@10 |
| **E3** | ⭐ 加重排序值不值？ | nDCG@10 + 延迟 |
| **E4** | 文档怎么切最好？ | Recall@10 |

### 1.2 ⭐ 五条纪律（全程执行）

```
① 一次只改一个变量        否则无法归因
② test 集只用一次         所有调参在 dev；test 用机械锁强制
③ 必须报告 BM25 基线      否则"提升"毫无意义
④ 必须报告成本            效果与延迟/编码时间同表
⑤ 提升必须做显著性检验     配对 t + 效应量 + bootstrap CI
```

### 1.3 ⭐ 评测工具的可信度（在报数字之前必须先证明）

**这是本项目最容易出问题的地方，所以做了三层验证：**

| 层次 | 手段 | 结果 |
|---|---|---|
| 单元测试 | 56 项（含 docs/05 全部人工算例） | ✅ 通过 |
| 真实数据交叉验证 | oracle / random / anti 三组极端排序 | ✅ 行为符合理论 |
| 独立实现重算 | 手写指标实现重算 run 文件 | ✅ 差异 <5e-5（仅四舍五入） |

> ⭐ **anti 组的关键作用**：Recall@100=1.0 但 nDCG@100 仅 0.19 —— 证明指标能区分
> "召回"与"排序质量"。**没有这个区分，E3（重排序）就无从设计。**

## 三、⭐⭐ 核心发现

### 发现 ①：换检索范式 ≫ 一切排序优化

![效应量对比](figures/fig5_effect_sizes.png)

| 改进手段 | nDCG@10 提升（dev） | Cohen's d | 量级 |
|---|---|---|---|
| BM25 调参（k1 1.5→0.7） | +2.05% | 0.114 | 可忽略 |
| 重排序（K=20） | +2.67% | 0.119 | 小 |
| 混合检索（RRF） | **-12.96%** | -0.479 | 负 |
| **换稠密检索（D1）** | **+38.2%** | **0.613** | **中** |

```
⭐ 工程含义：
  花 5 小时调 BM25 超参（+2.05%），不如花 70 秒编码一次向量（+38.2%）。
  排序层的所有优化加起来，也抵不过一次范式切换。
```

### 发现 ②：混合检索在质量悬殊时是负优化（**test 复现**）

![dev vs test](figures/fig4_dev_vs_test.png)

```
E1 曾给出"互补"信号：BM25 与 D1 的 top-10 只有 21.4% 重合
        ↓
但 E2 实测：RRF 融合后 nDCG@10 反而降低
        ↓
权重扫描的决定性证据：
   w_弱=0.00 → 0.8139（= 纯强方法）
   w_弱=0.05 → 0.8126
   w_弱=1.00 → 0.7085（等权，最差）
        ↓
⭐ 最优权重是「不混合」。互补性 ≠ 融合有收益。
```

**可复用的判断准则**：当两方法质量悬殊（nDCG 差 >50%）时，RRF 融合是负优化。

### 发现 ③：重排有效但收益脆弱（dev 显著，**test 未复现**）

![E3 K 曲线](figures/fig2_e3_k_sweep.png)

| K | nDCG@10（dev） | vs 第一段 | 延迟 |
|---|---|---|---|
| 0 | 0.8139 | — | ~0 |
| 10 | 0.8345 | +2.54% | 41 ms |
| **20** | **0.8356** | **+2.67%** | 83 ms |
| 50 | 0.8281 | +1.74% | 206 ms |
| 100 | 0.8211 | +0.88% | 413 ms |

**两个规律**：
- **K=20 是甜点**，更大的 K 反而更差（候选噪声干扰 cross-encoder），延迟却线性涨
- **test 上不显著**（+0.16%，p=0.625）：dev 的小效应量跨集未复现

> ⭐ 这是本项目**最有教育意义的发现**：
> dev 上 p=4e-28 的"高度显著"，在 test 上变成 p=0.625 的"无差异"。
> **统计显著 ≠ 泛化有效**，尤其当效应量只有 d=0.119 时。

### 发现 ④：分块在本数据上是负优化

| 策略 | BM25 nDCG@10 | 稠密 nDCG@10 |
|---|---|---|
| native（不切分） | **0.5305** | **0.8139** |
| fixed256 | 0.5218（-1.66%） | 0.7929（-2.58%） |
| fixed512 | 0.5276（-0.55%） | 0.8112（-0.33%） |
| paragraph | 0.5277（-0.54%） | 0.8111（-0.34%） |

**规律：块越小越差**。原因有三（详见 [docs/16](16-E4分块消融实验报告.md) §四）：
① 截断担忧被高估（只有 3.4% 段落过长，且这部分很少被标注）
② DuReader 的 passage 本身已是语义完整单元，硬切破坏语义
③ **段落级评测下分块有"位置稀释"的结构性劣势**（同一段落的多个块只占一个位置）

## 四、⭐⭐ dev → test 的泛化检验（本项目最重要的方法论产出）

| 结论 | dev | test | 复现？ | 教训 |
|---|---|---|---|---|
| 稠密 ≫ BM25 | +53.4%（d=0.822） | +55.1%（d=1.035） | ✅ 更强 | 大效应量稳定 |
| 混合负优化 | -13.0% | -12.8% | ✅ 复现 | 结构性原因稳定 |
| 重排有效 | +2.67%（p=4e-28） | +0.16%（p=0.625） | ❌ **未复现** | **小效应量脆弱** |

```
⭐ 三条结论的对比揭示了一个规律：
   效应量「大」（d>0.8）的结论 → 跨集稳定复现
   效应量「中」（d≈0.5）的结论 → 稳定复现
   效应量「小」（d≈0.1）的结论 → ⚠️ 可能不复现

   → 这给出一条实用的判断准则：
     做实验时若效应量 <0.2，即使 p 值极小，也不要急于下结论。
```

## 六、⭐ 实践建议（基于本项目数据）

```
如果只能改一件事：
    → 换稠密检索。+55.1%，d=1.035，收益最大

如果是一次性建索引成本敏感（如语料频繁更新）：
    → BM25 + 良好的分词仍是可接受的基线（0.5680 vs 0.8809，差距明确）

如果已经用了稠密检索，还想提升：
    → 先试重排（dev +2.67%，但要验证是否在你的数据上复现）
    → 不要试混合（本数据 -12.8%）
    → 不要试分块（本数据 -0.33% ~ -2.58%）

如果追求更低延迟：
    → BGE-small（0.7948）比 BGE-base（0.8809）慢不了多少但快 2 倍
       —— 但注意这是 GPU 数据，CPU 上 base 慢 3.6 倍
```

## 七、⚠️ 局限声明（必须与结论同读）

### 7.1 数据规模

本项目用 **10 万段落**，DuReader 全量是 **890 万段落**。
稠密检索的规模优势在小语料上可能被低估；BM25 在小语料上相对更强。
**结论不能外推到全量。**

### 7.2 数据领域

数据集源自**通用网页搜索**。垂直领域（医疗、法律、代码）的分词、
嵌入模型、分块策略都可能有不同结论。

### 7.3 评测范围

本项目评测的是**检索质量**（nDCG/Recall），**不是端到端 RAG 效果**。
检索指标高不等于生成答案好——生成阶段的正确性依赖 LLM 与提示词，
本项目未涉及。

### 7.4 dev/test 不对称

- dev 每 query 平均 **2.60** 个相关段落，test 为 **4.92**
- dev 正例保证在语料内（从 train 的正例抽取），test 是官方语料
- dev 与 test 有 1,328 个段落 id 重合（各 1.33%，同源语料，非泄漏）

**故 dev 与 test 的绝对指标不可直接比较**，只能看趋势与相对差异。

### 7.5 方法覆盖

未涉及：多向量检索（ColBERT 类）、领域微调、检索-生成联合优化、
learned sparse（SPLADE 类）、重排模型对比（只用了一个 bge-reranker-base）。

### 7.6 统计效力

- test 只有 2,000 query，对**小效应量**（d<0.2）的检验力有限
- 显著性检验用配对 t 检验 + bootstrap CI，未做多重比较校正
  （E2/E3 各做了多组比较，存在假阳性风险，但主要结论的效应量较大，不受影响）

### ⭐ 执行过程中发现并修正的自身错误（全部记录在案）

| 错误 | 性质 | 影响 | 处置 |
|---|---|---|---|
| `mrr_at_k` 用生成器而非集合 | 实现 bug | MRR 系统性偏低（26.6% query 受影响） | 修复 + 加类型多样性测试 |

| 复核脚本截断候选集 | 复核工具 bug | 误报"重排改变召回" | 判定为工具问题，实验本身正确 |

> ⭐ **这些错误的共同点：都不报错，只让结果悄悄错。**
