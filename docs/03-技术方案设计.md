## 一、总体架构

系统分为离线阶段与在线阶段：

- 离线阶段：原始语料（JSONL）经清洗、分块后，由嵌入模型编码，建立 FAISS 索引；同时建立 BM25 倒排索引（jieba 分词）
- 在线阶段：query 分别经 BM25 检索与嵌入 + FAISS 检索，两路结果经 RRF 融合，取 Top-100 候选，再由 Cross-encoder 重排，输出 Top-10，最后进入评测模块计算 nDCG/Recall

## 二、核心技术选型

### 2.1 检索层

| 组件 | 选型 | 理由 | 备选 |
|---|---|---|---|
| 稀疏检索 | rank_bm25 | 轻量、纯 Python、易读 | bm25s（更快） |
| 中文分词 | jieba | 成熟、零依赖 | pkuseg、HanLP |
| 稠密检索 | sentence-transformers + faiss | 标准组合 | FlagEmbedding |
| 嵌入模型 | BAAI/bge-small-zh-v1.5 | 中文效果好、约 100MB | bge-base、text2vec |
| 重排序 | BAAI/bge-reranker-base | 主流中文重排序 | bge-reranker-large |

嵌入模型以 BGE-small 为起点：体积小（约 100MB，8GB 显存甚至 CPU 可行），中文效果在 MTEB 中文榜表现良好，且便于后续对比实验（有 small 基线后再试 base 才有对照）。一上来就用最大的模型，跑得慢、调不动、且没有对比基准。

### 2.2 不使用的技术

| 技术 | 原因 |
|---|---|
| LangChain / LlamaIndex | 封装太厚，看不到 BM25 的 k1/b、RRF 的 k，无法做精细消融 |
| Elasticsearch | 需部署服务，对单机实验过重 |
| Milvus / Qdrant | 向量数据库服务化，本项目数据量不需要 |
| Docker | 单机实验无需容器化 |

核心原则是量化每个环节，因此必须能精确控制每一步，高层框架会把这个能力拿走，故选择手写核心逻辑，用底层库。

## 三、关键模块设计

### 3.1 检索器抽象接口

```python
from abc import ABC, abstractmethod
from typing import List, Tuple

class BaseRetriever(ABC):
    """检索器抽象基类，统一接口使不同检索器可互换、可组合。"""

    @abstractmethod
    def build_index(self, corpus: List[dict]) -> None:
        """离线建索引。"""

    @abstractmethod
    def search(self, query: str, top_k: int = 100) -> List[Tuple[str, float]]:
        """检索，返回 [(passage_id, score), ...]，按分数降序。"""
```

抽象基类保证所有检索器接口一致，使融合模块可接受任意检索器列表，后续加新检索器无需改动上层代码。

### 3.2 融合模块（RRF）

```python
def reciprocal_rank_fusion(
    result_lists: List[List[Tuple[str, float]]],
    k: int = 60,
) -> List[Tuple[str, float]]:
    """RRF 融合，只用排名而非原始分数，解决 BM25 分数与余弦相似度不可比的问题。"""
    scores = {}
    for results in result_lists:
        for rank, (doc_id, _) in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])
```

### 3.3 评测模块

指标实现必须断言 DCG <= IDCG（见评测协议），并为指标写单元测试，用"理想排序应为 1.0"这类确定性用例验证。指标代码有 bug 是最隐蔽且最致命的错误——它不报错，只是数字不对，而所有结论都建立在它上面。

## 四、配置管理

所有实验参数放 YAML，代码不写死：

```yaml
experiment:
  id: E3
  name: "重排序对比"

data:
  corpus_size: 100000
  dev_ratio: 0.1

retrieval:
  bm25:
    enabled: true
    k1: 1.5
    b: 0.75
  dense:
    enabled: true
    model: "BAAI/bge-small-zh-v1.5"
    batch_size: 64

fusion:
  method: "rrf"
  k: 60

rerank:
  enabled: true
  model: "BAAI/bge-reranker-base"
  top_n: 50

eval:
  ks: [1, 5, 10, 20, 100]
  metrics: ["recall", "mrr", "ndcg"]

runtime:
  seed: 42
  device: "cuda"
```

配置化的价值在于改一个数字就能跑一个新实验，这是做消融实验的前提。

## 五、可复现性设计

四条保证可复现的措施：

1. 固定随机种子（config 中写 seed，代码中设 numpy/torch/random）
2. 记录完整配置（每次实验把实际使用的配置存进 results/）
3. 记录环境（Python 版本 + 关键库版本）
4. 记录语料库规模与哈希

实验记录模板：

```json
{
  "experiment_id": "E3",
  "timestamp": "2026-10-20T14:30:00",
  "environment": { "python": "3.12.14", "device": "cuda" },
  "data": { "corpus_size": 100000, "queries": 2000 },
  "config": {},
  "results": {}
}
```

## 六、性能预算

基于 RTX 4060 8GB / 32GB RAM 的预估：

| 操作 | 数据规模 | 预估耗时 | 瓶颈 |
|---|---|---|---|
| 嵌入编码 | 10 万段落 | 约 5 分钟（GPU） | GPU |
| 嵌入编码 | 100 万段落 | 约 50 分钟（GPU） | GPU |
| FAISS 建索引 | 100 万向量 | 约 1 分钟 | RAM |
| BM25 建索引 | 100 万段落 | 约 10 分钟（jieba 分词） | CPU |
| 全量评测 | 2000 query | 约 10-60 分钟 | 检索方法 |

jieba 分词是 CPU 密集的，100 万段落分词可能比嵌入编码还慢，需缓存分词结果。

## 七、技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 依赖安装失败（torch/CUDA） | 阻塞 | 准备 CPU-only 降级方案，先装 CPU 版验证流程 |
| FAISS 在 Windows 装不上 | 阻塞 | 用 faiss-cpu，备选 hnswlib 或纯 numpy 暴力检索 |
| 嵌入模型下载慢 | 中 | ModelScope 镜像，或手动下载后指定本地路径 |
| 显存不足 | 中 | 减小 batch_size，或全 CPU 跑 |
| 数据规模超预期 | 中 | 严格按分阶段策略（1万→10万→100万） |
