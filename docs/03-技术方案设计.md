## 三、核心技术选型

### 3.1 检索层

| 组件 | 选型 | 理由 | 备选 |
|---|---|---|---|
| **稀疏检索** | `rank_bm25` | 轻量、纯 Python、易读 | `bm25s`（更快） |
| **中文分词** | `jieba` | 最成熟、零依赖 | `pkuseg`、`HanLP` |
| **稠密检索** | `sentence-transformers` + `faiss` | ⭐ 标准组合 | `FlagEmbedding` |
| **嵌入模型** | `BAAI/bge-small-zh-v1.5` | ⭐ 中文效果好、仅 ~100MB | bge-base、text2vec |
| **重排序** | `BAAI/bge-reranker-base` | ⭐ 主流中文重排序 | bge-reranker-large |

### 3.2 ⭐ 为什么嵌入模型选 BGE-small 作为起点

```
⭐⭐ 三个理由：

① 体积小（~100MB）→ 8GB 显存轻松，甚至 CPU 可行 ✅
② 中文效果在 MTEB 中文榜上表现优秀 ✅
③ ⭐ 便于后续【对比实验】
     —— 有了 small 基线，再试 base 才有"提升多少"的对照
        ↓
   ⚠️ 一上来就用最大的模型，是新手常犯的错误：
      跑得慢、调不动、且没有对比基准
```

### 3.3 ⚠️ 不使用的技术（及原因）

| 技术 | 为什么不用 |
|---|---|
| **LangChain** | ⚠️ 封装太厚，**看不到 BM25 的 k1/b、RRF 的 k**，无法做精细消融 |
| **LlamaIndex** | 同上 |
| **Elasticsearch** | ⚠️ 需部署服务，**对单机实验过重**；`rank_bm25` 够用 |
| **Milvus / Qdrant** | ⚠️ 向量数据库服务化，**本项目数据量不需要**；FAISS 文件索引更简单 |
| **Docker** | ⚠️ 单机实验无需容器化（可作为加分项） |

> 🎯 **核心理念**：
> ```
> ⭐ 本项目的目标是【量化每个环节】
>    → 必须能【精确控制每一步】
>    → 高层框架会把这个能力拿走
>        ↓
>    所以选择"手写核心 + 用底层库"
> ```

## 四、⭐ 关键模块设计

### 4.1 检索器抽象接口

```python
# src/retrieval/base.py 的设计
from abc import ABC, abstractmethod
from typing import List, Tuple

class BaseRetriever(ABC):
    """检索器抽象基类。

    ⭐ 统一接口，使得不同检索器可以互换、可组合。
    """

    @abstractmethod
    def build_index(self, corpus: List[dict]) -> None:
        """离线建索引。"""

    @abstractmethod
    def search(self, query: str, top_k: int = 100) -> List[Tuple[str, float]]:
        """检索。

        Returns:
            [(passage_id, score), ...]  按分数降序
        """
```

> ⭐ **为什么要有抽象基类**：
> ```
> ① 保证所有检索器【接口一致】→ 可以互换、可以做消融
> ② 融合模块（E2）可以接受【任意】检索器列表
> ③ 后续加新检索器（如 ColBERT）无需改动上层代码
> ```

### 4.2 ⭐ 融合模块（RRF）

```python
# src/retrieval/hybrid.py 的核心逻辑
def reciprocal_rank_fusion(
    result_lists: List[List[Tuple[str, float]]],
    k: int = 60,
) -> List[Tuple[str, float]]:
    """RRF 融合。

    ⭐ 关键：只用【排名】，不用原始分数
        → 解决 BM25 分数与余弦相似度不可比的问题

    Args:
        result_lists: 多个检索器的结果，每个是 [(id, score), ...]
        k: 平滑常数（通常 60）
    """
    scores = {}
    for results in result_lists:
        for rank, (doc_id, _) in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])
```

## 五、配置管理

**⭐ 所有实验参数放 YAML，代码里不写死：**

```yaml
# configs/e3_rerank.yaml 示例
experiment:
  id: E3
  name: "重排序对比"

data:
  corpus_size: 100000        # ⭐ 必须记录规模
  dev_ratio: 0.1

retrieval:
  bm25:
    enabled: true
    k1: 1.5
    b: 0.75
  dense:
    enabled: true
    model: "BAAI/bge-small-zh-v1.5"
    batch_size: 64

fusion:
  method: "rrf"
  k: 60

rerank:
  enabled: true
  model: "BAAI/bge-reranker-base"
  top_n: 50                  # ⭐ 重排多少个候选

eval:
  ks: [1, 5, 10, 20, 100]
  metrics: ["recall", "mrr", "ndcg"]

runtime:
  seed: 42
  device: "cuda"
```

> ⭐ **配置化的价值**：**改一个数字就能跑一个新实验**——这是做消融实验的前提。

## 七、性能预算

**⭐ 基于实际硬件（RTX 4060 8GB / 32GB RAM）的预估：**

| 操作 | 数据规模 | 预估耗时 | 瓶颈 |
|---|---|---|---|
| 嵌入编码 | 10 万段落 | ~5 分钟（GPU） | GPU |
| 嵌入编码 | 100 万段落 | ~50 分钟（GPU） | GPU |
| FAISS 建索引 | 100 万向量 | ~1 分钟 | RAM |
| BM25 建索引 | 100 万段落 | ~10 分钟（jieba 分词） | CPU |
| 单次检索 | — | ~10-500ms | 方法而定 |
| 全量评测 | 2000 query | ~10-60 分钟 | 检索方法 |

> ⚠️ **注意**：**jieba 分词是 CPU 密集的**，100 万段落分词可能比嵌入编码还慢。
> **应对**：缓存分词结果（pickle 到磁盘）。

## 八、⚠️ 技术风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **依赖安装失败**（torch/CUDA） | ⚠️ 阻塞 | 准备 CPU-only 降级方案；先装 CPU 版验证流程 |
| **FAISS 在 Windows 装不上** | ⚠️ 阻塞 | 用 `faiss-cpu`；备选 `hnswlib` 或纯 numpy 暴力检索（小规模可行） |
| **嵌入模型下载慢** | 中 | ModelScope 镜像；手动下载后指定本地路径 |
| **显存不足** | 中 | 减小 batch_size；或全 CPU 跑（慢但可行） |
| **数据规模超预期** | 中 | ⭐ 严格按分阶段策略（1万→10万→100万） |
