### ⚠️ 当前最高优先级问题

**`mrr_at_k` 存在真实 bug —— 已于 2026-10-24 修复并量化影响**

```
位置：src/eval/metrics.py:84-93（修复前）
问题：rel = (str(x) for x in relevant)   ← 生成器，不是集合
后果：1) `if not rel` 永远为 False（生成器对象恒为真）
      2) 生成器只能消费一次，循环内 `d in rel` 会「吃掉」元素
      → 只有「第一个正例恰好排在第 1 位」时才算对，其余全部算成 0
```

**实测影响（dev 8,640 query，BM25 基线）**：

| 情形 | query 数 | 占比 | bug 下的结果 |
|---|---|---|---|
| 第一个正例在第 **1** 位 | 4,092 | 47.4% | ✅ 算对（1.0） |
| 第一个正例在第 **2–10** 位 | 2,295 | **26.6%** | ❌ 算成 0（应为 1/rank） |
| 前 10 无正例 | 2,253 | 26.1% | ✅ 碰巧算对（0.0） |

| 指标 | bug 版 | 正确值 | 误差 |
|---|---|---|---|
| **MRR@10** | 0.473611 | **0.562053** | **+0.0884（15.7% 相对）** |

**为什么危险**：它不报错、不崩溃，只是让指标**系统性偏低**，而
[docs/05](05-评测协议.md) 第一句话就是"如果指标算错，后面所有结论都是错的"。

**修复状态**：

| 项 | 状态 |
|---|---|
| 代码修复（改回集合推导） | ✅ 已完成 |
| 防回归测试（输入类型多样性 4 项） | ✅ 已完成 |
| 全量测试 | ✅ **56/56 通过** |
| MRR 正确值确认 | ✅ 0.562053（与修复前结果文件里的 `mrr@10` 一致） |

> ⭐ **一个重要的澄清**：已完成的 BM25 结果文件里 `mrr@10 = 0.562053` **本来就是正确值**。

### P1 · BM25 提速（预计 2–3 小时）

| ID | 任务 | 状态 | 验收标准 |
|---|---|---|---|
| **P1-1** | 实现倒排索引版 BM25（scipy 稀疏矩阵） | ⏳ 待做 | 同参数下结果与 `rank_bm25` 一致（top-100 重合率 >99%） |
| **P1-2** | 速度基准对比 | ⏳ 待做 | 目标 <10 ms/query（当前 145 ms） |
| **P1-3** | 替换 `run_e1_bm25.py` 的检索后端 | ⏳ 待做 | 全流程跑通且指标不变 |

**为什么要做**（不是过度优化）：

```
当前：145 ms/query × 8,640 query = 21 分钟 / 组
网格调参 16 组 = 5.6 小时
        ↓
提速到 10 ms/query 后：1.4 分钟/组，16 组 = 23 分钟
        ↓
省下 5 小时，且后续 E2/E3 每次都要重跑检索
```

**技术方案**：`scipy.sparse` 存 (term × doc) 矩阵，一次矩阵乘法算出所有 query 的分数。
风险：内存占用上升（20M tokens 的稀疏矩阵约 200–400 MB），需实测。

```powershell

.venv\Scripts\python.exe -m unittest discover -s tests
```
