## 零、⭐ 本报告要回答什么

> **Q3：加重排序值不值？**
>
> 拆解为两个必须同时回答的子问题：
> - **效果**：nDCG@10 提升多少？（重排只改顺序不改召回，故主指标是 nDCG）
> - **成本**：每 query 多花多少时间？K（重排候选数）如何影响效果与成本？

**⭐ 这个项目存在的意义就是这张"效果-成本"权衡表**——
"提升 5% 但慢 10 倍"与"提升 5% 只慢 20%"是完全不同的结论。

---

## 一、⭐ 两阶段架构：为什么必须重排（docs/06 §3.2/3.3）

| | 第一段：稠密检索（bi-encoder） | 第二段：重排序（cross-encoder） |
|---|---|---|
| 结构 | query、passage **各自独立**编码 | query + passage **拼接进同一模型** |
| 交互 | 无（向量点积） | 深度交互（attention 全程） |
| 精度 | 较低 | 高 |
| 速度 | 极快（索引 + 一次编码） | 慢（每候选一次前向） |
| 适用 | 从 10 万段召回 top-K | 对 top-K 精排 |

```
稠密检索：N 段编码一次（离线）+ 每 query 一次编码 + 一次向量检索
重排序：  每 query 要对 top-K 候选【逐个】过一遍 cross-encoder → K 次前向
        ↓
⭐ K 越大候选越全，但延迟线性增长 → K 的选择是效果-成本的核心权衡
```

---

## 二、实验设置

| 项 | 值 | 说明 |
|---|---|---|
| 第一段检索器 | **D2 / BGE-base**（纯稠密） | ⭐ E2 已证伪混合，故用最强单方法 |
| 第一段深度 | top-100 | 重排只在这 100 个候选内进行 |
| 重排模型 | `BAAI/bge-reranker-base` | cross-encoder |
| 重排候选数 K | {10, 20, 50, 100} | docs/06 §3.5 的关键变量 |
| 主指标 | **nDCG@10** | 重排只改顺序 |
| 成本指标 | 每 query 延迟（ms） | 估算：每对延迟 × K |
| 环境 | GPU + fp16 | |

### ⭐ 实现的关键效率决策

对 864,000 个 (query, passage) 对，如果对每个 K 档都重新打分要跑 4 遍。
本项目做法：**对 top-100 候选只打一次分**，之后各 K 档只是取重排结果的前 K 个，
**4 档评测只需 1 次打分**（省 4 倍时间）。

### 3.1 K 网格：效果-成本权衡（E3 的核心结论）

**全量 8,640 query，第一段 = D2（BGE-base），重排 = bge-reranker-base，GPU fp16**

| K（候选数） | nDCG@10 | Recall@10 | vs 第一段 | 估算延迟/query |
|---|---|---|---|---|
| 0（不重排） | 0.8139 | 0.8875 | — | ~0 ms |
| 10 | 0.8345 | 0.8875 | +2.54% | 41 ms |
| **20** | **0.8356** | **0.9005** | **+2.67%** | **83 ms** |
| 50 | 0.8281 | 0.8937 | +1.74% | 206 ms |
| 100 | 0.8211 | 0.8864 | +0.88% | 413 ms |

**⭐⭐ 两个关键规律**：

```
规律一：K=20 是甜点，更大的 K 反而更差
  nDCG@10：0.8345 → 0.8356 → 0.8281 → 0.8211（K=10→20→50→100 单调降）
  → 候选越多，混入的不相关段落越多，cross-encoder 被噪声干扰
  → 「候选越多越好」是错的，存在最优 K

规律二：延迟随 K 线性增长
  每对打分 4.13 ms × K → 41 → 83 → 206 → 413 ms
  → K=100 的延迟是 K=20 的 5 倍，但效果更差
```

## 四、⭐ 结论（Q3 的答案）

### ✅ 重排值不值？——**值，但有三个明确的前提**

```
答案：K=20 时 nDCG@10 从 0.8139 → 0.8356（+2.67%），
      统计显著（p=4.0e-28），代价是每 query 多花 83 ms。
```

**但要把话说全（这三个限定缺一不可）：**

**① 效应量小（Cohen's d = 0.119）——提升是"微调"，不是"质变"**

```
⭐ 本项目三个改进手段的效应量对比（这是全局最有价值的一张表）：

| 改进方式 | nDCG@10 提升 | Cohen's d | 量级 |
|---|---|---|---|
| BM25 调参 | +2.05% | 0.114 | 可忽略 |
| 重排序（K=20） | +2.67% | 0.119 | 小 |
| ⭐ 换稠密检索 | +38.2% | 0.613 | 中 |

  → 排序优化（调参/重排）都是"雕虫"，换检索范式才是"换刀"
  → 工程含义：先上稠密检索，再考虑要不要为重排付出 83ms
```

**② K=20 是甜点，更大的 K 得不偿失**

```
K:    10 → 20 → 50 → 100
效果: +2.54% → +2.67% → +1.74% → +0.88%   （越大越差）
延迟:  41ms → 83ms → 206ms → 413ms          （线性增长）
        ↓
  ⭐ "候选越多越好"是错的——超过 20 后，混入的噪声段落
     让 cross-encoder 反而排得更差，且延迟还在涨
```

**③ 收益依赖第一段的强度**

本实验第一段是 D2（已很强，nDCG@10=0.8139）。重排在强第一段上的
提升空间天然被压缩——第一段把正例排得越靠前，重排能改的越少
（53.8% 的 query 重排后毫无变化）。

### ⚠️ 一个必须诚实报告的对照：小样本高估了全量

| | K=20 的 nDCG@10 提升 |
|---|---|
| 500 条调试子集 | +5.60% |
| **全量 8,640** | **+2.67%** |

> 前 500 条 query 比整体偏易（子集 0.8105 vs 全量 0.8139 的第一段基线）。
> **这就是为什么本项目坚持"小样本验证流程、全量才下结论"**——
> 如果用 500 条的 +5.6% 写报告，会把效果高估一倍。

## 五、⚠️ 已知局限

| # | 局限 | 影响 |
|---|---|---|
| 1 | 第一段已很强（D2 nDCG@10=0.8139） | 重排的提升空间被压缩；第一段弱时重排收益通常更大 |
| 2 | 延迟是按"每对延迟×K"的估算 | 实际部署的批处理/并行会改变绝对延迟，但"随 K 线性增长"的趋势不变 |
| 3 | 只用 bge-reranker-base 一个模型 | 未对比其他重排模型（bge-reranker-large 等） |
| 4 | dev 集 | 绝对值不可与 test 横比 |
| 5 | 打分用了 fp16 | 与 fp32 可能有极小差异（未消融，量化为 <0.1% 量级） |
